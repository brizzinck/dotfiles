# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repo Is

Personal dotfiles for an Arch Linux / Hyprland / Wayland setup, managed with **GNU Stow**. Running `stow .` from the repo root symlinks everything into `$HOME`, mirroring the directory structure. Non-config files are excluded via `.stow-local-ignore`.

## Setup

```bash
git clone --recursive <repo>
git submodule update --init --recursive
chmod +x install.sh && ./install.sh
```

`install.sh` does a full machine bootstrap: pacman packages, AUR (via yay), Flatpak apps, Go/NPM/Rust toolchains, Oh My Zsh, Docker setup, SSH key generation, then runs `stow .` to link the dotfiles and `browsers/apply.sh` to copy the browser settings. Root-level system changes (packages, `/etc`, timers, fstab, grub) are applied separately by `sudo ./apply-system.sh`; `./doctor.sh` verifies the result.

After modifying dotfiles, re-apply with:
```bash
cd ~/dotfiles && stow .
```

## Architecture

### Config layout
All configs live under `.config/` following XDG Base Dir. Root-level files (`.zshrc`, `.gitconfig`) stow directly to `$HOME`.

### Monitor management
Static Hyprland rules in `.config/hypr/monitors.lua` (loaded by `hyprland.lua` with `dofile`; `scripts/lid.sh` re-applies the panel rule from the same table): `HDMI-A-1` 2560x1440@144 at `0x0`, the laptop panel `eDP-1` 2880x1800@120 scaled 1.5 at `0x1440` (below the external one), plus a `preferred, auto` fallback for any other output. Hyprland applies them on hotplug, so there is no kanshi, no polling script and no monitor daemon.

### Hyprland config (Lua)
`.config/hypr/hyprland.lua` (+ `monitors.lua`) is the only Hyprland config; there is no `hyprland.conf` (`doctor.sh` checks that it is absent and that the running instance loaded the Lua file). hyprlock, hypridle and the screensaver stay hyprlang. In a Lua config `hyprctl keyword` is gone and `hyprctl dispatch` takes a Lua expression: scripts call `.local/bin/hyprd` (legacy dispatcher names, e.g. `hyprd focuswindow address:0x..`) or `hyprctl eval '<lua>'`. Binds are `hl.bind("SUPER + X", hl.dsp..., { description = "..." })` (descriptions feed the cheatsheet, the hub and `docs/keymap.md`; no commas). `hyprctl binds -j` reports Lua binds as dispatcher `__lua`, so nothing can be read back from it: `hyprland.lua` wraps `hl.bind` and records every dispatcher in a registry, and `hyprctl eval 'df_bind_run("SUPER+Return")'` replays one (mods in SUPER CTRL ALT SHIFT order, key as in the live table, case-insensitive). The hub uses that for its keybind rows (`kind bind`) and for the leader. Hyprland 0.55/0.56 runs a `catchall` bind next to the matching bind and on a lone modifier press (hyprwm/Hyprland#15063), so the repeat modes (`resize`, `mouse`) leave through `leave_on_other_key()`, which ignores the event while one of the mode's own keys or a modifier is held.

### Theme system
Idle (`.config/hypr/hypridle.conf`): dim at 150 s, at 300 s a clock-only hyprlock screensaver (`screensaver.conf`, started by `scripts/screensaver.sh`, no password; any input dismisses it via hypridle on-resume + `SIGUSR1`), panel off (`dpms`) at 1200 s. The machine never suspends or locks by itself, and nothing is killed. All listeners are skipped while media plays or an automation Chrome runs (`idle-allowed.sh`; Wayland/DBus inhibitors are honoured too). `SUPER+Escape` is still the real password lock.

The palette is **Everforest v2** with two switchable variants: **black** (default, pure `#000000` backgrounds) and **night** (near-black `#0a0e0c` content background; bar, lock screen, screensaver and the Hyprland background stay `#000000`). fg, accents and ANSI 0-15 are shared. Source of truth: `themes/palette/everforest.json` (tokens) with the human-readable `themes/palette/palette.md` (token roles, per-app mapping, owner steps). `themes/palette/render.py` (stdlib Python, `PYTHONPYCACHEPREFIX=/tmp/pycache python3 themes/palette/render.py`, `--check` for doctor) renders every `templates/*.tmpl` for both variants into the committed `themes/generated/{black,night}/`; a new app only needs a new template. The active variant is the symlink `~/.local/state/theme/current -> themes/generated/<variant>`, and `theme black|night|toggle|status|init` (`.local/bin/theme`, hub row "Theme: black / night") flips it, reloads ghostty (SIGUSR2), alacritty, every tmux server of the user and nvim, then runs the hooks in `.config/theme/hooks.d/` (`10-hyprland` reload + configerrors check, `20-waybar` SIGUSR2, `30-dunst` `dunstctl reload`, `40-swayosd` restart, `50-qt`). A missing link is recreated as black by `install.sh`, `.zshrc`, tmux.conf and the first Hyprland autostart line.

Window look (`hyprland.lua` + the fragment): solid calm colours, no gradient and no shadow. Active border `green_soft`, inactive `line` (almost invisible; the gaps separate tiles), group border and active groupbar tab `purple_soft`, blocked grouping `yellow_soft`. Hyprland renders `round(border_size * scale)` physical pixels and rounds every box to whole pixels, so `border_size` (2 = 2 px on HDMI-A-1, 3 px on eDP-1) and the gaps (4 = 4 / 6 px) must be even to stay crisp at scale 1.5 (odd sizes round up: 3 -> 5 px); `rounding_power = 2`. A two-colour gradient on a 2-3 px stripe bands visibly and was the pixelated look. How each app follows the variant: `hyprland.lua` `dofile`s the black fragment (fallback) and then `current/hyprland.lua` inside `pcall` (a missing or broken fragment is skipped with a notification, black stays); hyprlock and the screensaver (hyprlang) `source` the black fragment and then `current/` (a missing sourced file is a config error, hence the fallback); waybar, wofi, swayosd and both GTK versions `@import` a repo symlink `theme-black.css` plus `theme.css` -> `current/...`; rofi `@import`s the same pair of paths; dunst reads `dunstrc.d/40-theme-black.conf` and `50-theme.conf` drop-ins; btop (`themes/everforest-v2.theme`) and qt6ct (`colors/everforest.conf`) are symlinks to `current/`; lazygit merges `current/lazygit.yml` through `LG_CONFIG_FILE` (set by `.zshrc`, tmux and hub); lazydocker uses ANSI names, so it follows the terminal palette. Literals that cannot follow (pango spans in `waybar/config`, workmux icons) hold token hex and are checked by `doctor.sh`. Generated but applied by hand: `everforest-<variant>.tdesktop-theme` (Telegram), `obsidian.css`, `claude-theme.json`; GTK/Qt apps pick up a switch at their next start. Owner steps are in `themes/palette/palette.md`. `themes/static/everforest-black/` only holds a pointer note now; the other directories in `themes/static/` (rose-pine, dracula, catppuccin-mocha, ...) and `themes/templates/` (matugen, wallust, pywal) are unused leftovers of the old HyprDynamicMonitors setup.

Wallpaper (W2): the owner's two-tone art is a committed vector, `themes/palette/templates/wallpaper.svg.tmpl` (potrace trace; figure `green_soft` on `bg_oled`) rendered into `themes/generated/{black,night}/wallpaper.svg`; no raster is ever committed (the source PNG stays in `~/pics/walls/`, the re-trace recipe is in the header of the script). `.config/hypr/scripts/wallpaper.sh apply|render|status [--dry-run] [--force]` reads `current/wallpaper.svg`, renders one PNG per output from `hyprctl monitors -j` at its native PHYSICAL size with `rsvg-convert` into `~/.cache/wallpaper/<output>-<WxH>-<hash>.png` (the 16:9 art is fitted whole and centred, so on the 16:10 panel the rest is the same black; never cropped) and keeps exactly one `swaybg -o NAME -i FILE -m fill` per output (only changed instances restart). It runs from the autostart, the `monitor.added` hook, `SUPER+O` (`--force`) and the theme hook `60-wallpaper.sh`; doctor `wallpaper` checks it.

### Bar (waybar)
Two bar objects per output in one waybar process (`.config/waybar/config` includes `modules.jsonc` and a state file each): **compact** (base bar, exclusive zone) and **full** (non-exclusive overlay with `margin-top: -28`, drawn over compact). `SUPER+B` = compact/full (`scripts/bar.sh mode toggle`, SIGUSR1 reaches only the full bar, so the exclusive zone and windows never move), `SUPER+CTRL+B` = hide/show everything (`bar.sh hide toggle`, a reload). State: `~/.local/state/waybar/{mode,hidden}`; `bar.sh render` writes `compact.jsonc`/`full.jsonc` (`start_hidden`) that the config includes, so the mode survives restarts, theme reloads (`bar.sh reload`) and logins (`bar.sh init` clears `hidden`). **Never send SIGUSR1 by hand**; a toggle leaves `$XDG_RUNTIME_DIR/waybar-bar/stale`, and the `monitor.added` hook runs `bar.sh sync --if-stale` so a new monitor gets the right mode. Signals (`pkill -o -u $(id -u) -RTMIN+N -x waybar`, `-o` so a script child that is still named waybar is not hit): 8 toggles drawer and summary, 9 updates, 15 vault; the recording module is a continuous script. Scripts print `class` = `normal|dim|enabled|warning|critical`, `style.css` maps them to palette tokens (green active/enabled, calm yellow_soft warning and red_soft critical tints without pill or bold, everything else grey; the AI module is never highlighted, an exhausted limit is normal; its text is `C 26·4  X –·100` = Claude and Codex % used, 5h·weekly, `–` = no data, from `ai-usage.sh`). Alert modules print nothing until relevant; `cache.sh` shares one run of the expensive ones (health, updates, ai) between the two bars; `toggles.sh` is the single source of the switch states (`ns`, microphone noise suppression, is the one switch whose normal state is on: the summary lists it only when it is off or the chain is broken, class `warning`; see "Audio"); `toggles.sh summary [--alert]` (both bars, every 10 s) runs its probes once per 8 s through `cache.sh toggles 8 -- toggles.sh summary-raw` and derives the compact `--alert` text from the cached full JSON (class `dim` = all off = empty text), and every toggle action (`toggles.sh`, `power-profile.sh`, `lid.sh`, `keep-awake.sh`, `idle-toggle.sh`, `mcp-telegram-send`, the night-light and DND binds) deletes `$XDG_RUNTIME_DIR/waybar-cache/toggles.json` before its RTMIN+8 poke; `power-profile.sh get` asks the tlp-pd D-Bus API (`busctl --system get-property`, 4 ms) before `tlpctl get` (170 ms), never `/sys/firmware/acpi/platform_profile` first (tlp-pd balanced on battery shows `low-power` there). `media.sh --follow` kills its `playerctl --follow` child on TERM/INT/HUP/EXIT (it used to leave one orphan per waybar restart). The compact -> full switch is animated by a GTK CSS opacity transition on the full bar (`style.css`): SIGUSR1 only moves that surface between layers, which never maps or unmaps it, so Hyprland layer rules and animations cannot fire (checked: no openlayer/closelayer events); drawers use waybar's own 220 ms revealer. Click grammar: L main, R menu, M quick binary action, scroll value; menus are fzf-menu based. Every tooltip ends with the same hint line, `L: x · M: y · R: z · Scroll: w` (that order, lowercase actions, idle buttons omitted). `WAYBAR_LOG_LEVEL=debug bar.sh restart` logs the GTK widget tree (`$XDG_RUNTIME_DIR/waybar-bar/waybar.log`). doctor checks bar-state, bar-layers (surfaces with the layer namespaces `waybar-compact` / `waybar-full` per monitor), bar-reserved, bar-css. **Watchdog**: `scripts/waybar-run.sh` is a supervisor, not an `exec`: waybar is its child and an abnormal exit (signal, non-zero status) restarts it after 1/2/5/10 s (`journalctl -t waybar-run` has status or signal), one low-urgency "Waybar crashed and was restarted" notification once it stayed up 5 s, and 5 crashes within 120 s end the loop with one "Waybar keeps crashing" notification (`bar.sh restart` starts it again). It checks (never blindly starts) the `ws-ipc-proxy.py` and `pinned-watch.py` daemons on each round, so a restart does not duplicate them. Status 0, SIGTERM/SIGINT/SIGHUP and a vanished Wayland socket are no crash; `bar.sh restart` first stops the supervisor with SIGTERM (pidfile `$XDG_RUNTIME_DIR/waybar-bar/supervisor.pid`, flock `supervisor.lock`; it forwards the SIGTERM to waybar) and then starts a new one, so `reload`/`hide` (SIGUSR2) and a restart never look like a crash; doctor `bar-watchdog`. Crash traces: `DEBUGINFOD_URLS` is already set (`/etc/profile.d/debuginfod.sh`, libdebuginfod comes with `libelf`; the `debuginfod` package, which is only the server and `debuginfod-find`, is not installed and not needed), so `coredumpctl debug waybar --debugger-arguments="-batch -ex 'set debuginfod enabled on' -ex 'thread apply all bt 25'"` symbolizes a good core. The waybar cores seen so far are `truncated` (1-2 MB, `coredumpctl list waybar`), so gdb stops with "Cannot access memory" and `coredumpctl info` shows `#0 n/a`: until a full core exists the only evidence is the signal in the journal and the `waybar.log` lines before it (the one SIGABRT caught while testing the watchdog came right after a burst of SIGUSR2 reloads).

**Panel off = frozen layout state**: Hyprland finishes frame-driven work only inside a render pass, and a dpms-off output presents no frames (hypridle `dpms off` after 20 min idle). Two things therefore stay stale until the panel wakes: the closing fade of a layer (after `bar.sh restart` a `waybar-compact` ghost with `pid: -1` stays in `hyprctl layers`) and the fade-out of the Hyprland error bar (a config error from a reload creates it; the next error-free `hyprctl reload` or `hyprctl seterror disable` only queues the destroy, `ErrorOverlay::draw` finishes it). While the bar is up it reserves `(text height + 10 * scale) / scale` at the top of the focused monitor (two lines at 1.5 = 61 px), so `monitors[].reserved` reads 89 instead of 28, the bars and tiled windows sit 61 px lower (`solitaryBlockedBy` contains `CONFIGERROR`), and nothing in `configerrors` explains it. Waking the panel clears it by itself; doctor `bar-layers` / `bar-reserved` skip a dpms-off output (`bar-panel-off` INFO) and name the error bar when it is the reason on an awake one. Do not chase it with more `bar.sh restart` / reloads while the panel is dark.

The health badge (`custom/health`, `health.sh` over `failed.sh`) also puts the machine-readable `items` (failed units, restart-looping units, sysalert conditions, each with a one-line reason such as the last error line of the unit journal; the tooltip lists the same lines) into its JSON; the left click runs `scripts/health-details.sh`, a fzf-menu list over that same cached run (preview: `systemctl [--user] status` + last 30 journal lines; Enter: restart, stop, stop+disable, reset-failed, journal in less; hub row `failed-units`, leader `s f`), so badge and view cannot disagree. The badge runs through `health-badge.sh` (module signal 16), which stores the exact output it displays as `waybar-cache/health-shown.json`; the view lists that snapshot, marks items that cleared since as `cleared` with a note and pokes the badge (RTMIN+16) so it catches up. A stopped or disabled unit is inactive and never raises an alert, and so is a unit in a normal start job (D-Bus activated daemon, oneshot run by a timer: `activating`, 0 restarts): a unit counts as looping only after `min_restarts` (2) restarts while auto-restarting/activating, and alerts when that holds on two consecutive runs or at 5 restarts. The "reason" of a unit says what the journal really holds (the journal is readable for the owner; a unit that only logged systemd start/stop lines gets that wording, not "not readable"). The bredllm tunnels (`voicebox-tunnel`, `bredllm-reverse-socks`) were removed on the owner's request; their unit files are backed up in `~/.local/share/workstation-overhaul/bredllm-units-backup/`.

Pinned apps (right side of both bars, `group/pinned`): the list is `.config/waybar/pinned.tsv` (id, label, glyph, window-class regex, launch command, notification regex; Telegram, Zen, Chrome, Obsidian, YouTube Music, Bitwarden). **Adding an app = one row, then `bar.sh reload`**: `bar.sh render` runs `scripts/pinned.sh gen`, which writes `custom/pin#ID` per row plus the group into `~/.local/state/waybar/pinned.jsonc`, included by both bars. One daemon, `scripts/pinned-watch.py` (started by `waybar-run.sh`, restarted by the module script if it died, survives bar restarts), follows the Hyprland event socket (open/close/move/focus) and a read-only session-bus monitor of `org.freedesktop.Notifications.Notify`; it renders `$XDG_RUNTIME_DIR/pinned/<id>.json` (what the module prints) and pokes waybar with **RTMIN+14**. `pinned.sh gen` makes the first pin run `pinned.sh module ID` (prints the file and restarts a dead daemon: the one place that does) and every other pin `cat` the file (`cat "$XDG_RUNTIME_DIR/pinned/ID.json" 2>/dev/null || pinned.sh module ID`; the script is only the fallback while the file does not exist), so a poke costs 2 bash starts instead of 12. Classes: `dim` not running, `normal` running, `focused` in front (fg), `new` (soft `yellow_soft` text, no pill). A notification whose app_name or desktop-entry matches the row's regex sets `new/<id>` unless the app is focused; it works with do-not-disturb on (dunst paused still receives the call; no dunst rule is involved); focusing the app, middle click or the menu's "Mark read" clears it. Click grammar: L focus (repeat = next window of the app; launches it when it has no window), M mark read, R fzf-menu (windows, New window / Launch, Mark read, Close all windows; protected classes ask first). `pinned.sh check` (doctor `pinned`) verifies list, generated modules and daemon; `pinned.sh edit` opens the list. `SUPER+T` / `SUPER+S` / `SUPER+N` (Telegram, YouTube Music, Obsidian) call `pinned.sh click ID`, so a bind and the bar's left click focus, cycle and launch the same way (`pinned.sh click ID --dry-run` shows what it would do).

Custom **Everforest-Cursor** (Bibata Modern vector art; fill `green` #abc682 (the former light `fg` fill looked like plain white Bibata), outline `bg_oled`, busy-cursor pies `bg_oled` (dark on the green disk; they are drawn at 80% opacity); hyprcursor SVG + XCursor of the same artwork, size 32 = 48 px on the 1.5 panel). It is a local package: `infrastructure/cursor/everforest-cursor-theme/PKGBUILD` (git source pinned by commit, colours from `themes/generated/black/pointer.json`), built as the owner by `infrastructure/cursor/build.sh` and installed with `pacman -U` into `/usr/share/icons` (so flatpaks see it) by `sudo ./apply-system.sh --only install`; `install.sh` runs the same build. `hyprland.lua` sets `HYPRCURSOR_THEME`/`XCURSOR_THEME` to it only when the theme directory exists, else `XCURSOR_THEME=Bibata-Modern-Ice` (Bibata stays installed as the fallback) and no `HYPRCURSOR_THEME`; Hyprland writes gsettings `cursor-theme`/`cursor-size` from those variables at login (`.config/gtk-3.0/settings.ini` has no cursor keys on purpose), `.local/share/icons/default/index.theme` inherits `Everforest-Cursor,Bibata-Modern-Ice,Adwaita`. `cursor-apply` switches a running session after the install (`--revert` goes back to Bibata, `--status` shows both). `hyprctl setcursor` also writes gsettings `cursor-theme`, so a test with another theme leaves it behind (it had become `Bibata-Modern-Amber`): `cursor-apply` is the only right way to switch the pointer, and doctor `cursor-gtk` fails when gsettings differs from the expected theme. The autostart runs `cursor-apply --boot` (waits up to 6 s until `hyprctl` answers, gsettings + `hyprctl setcursor`, one retry, result in `journalctl -t cursor-apply`) instead of a bare `hyprctl setcursor`; in Hyprland v0.56.2 the `hl.env` variables already reach the cursor manager on a clean start (it is created in `initServer` after the config ran; libhyprcursor reads `HYPRCURSOR_THEME`), so `--boot` is the safety net. The greeter's Hyprland uses the same `hl.env` selection. doctor: `cursor` (installed, complete, stamp current, fill = green, busy disk), `cursor-gtk`, `cursor-boot`, `cursor-env`.

### Launcher
**rofi** is only the app launcher (`$menu`, `SUPER+space`; `.config/rofi/`): it has no modes, so it gets the list grammar as far as rofi allows (`Ctrl+j/k` move, `Ctrl+d/u` page, `Esc` cancel, Cyrillic twins generated from `ROFI_OVERRIDES` in `layout.py`). wofi stays installed and is themed, but nothing binds it.

**Every other menu is the shared modal fzf** (V1b): `.config/fzf/vimfzf.sh` (sourced by scripts: `vimfzf ARGS`, `VF_PROMPT`, extra NORMAL-mode letters through `VF_NORMAL_BINDS` / the env `FZF_MENU_NORMAL_BINDS`) is a Telescope-like list: it opens in INSERT (typing filters, `Ctrl+j/k n/p`, `Ctrl+d/u`), `Esc` is NORMAL (`j/k g/G`, `i a /` back to INSERT, `q`/`Esc` quit; every other printable key is ignored; the mode tag `[I]`/`[N]` is in the prompt), ua/ru twins come from `lk_fzf_bind`, colours from `FZF_DEFAULT_OPTS_FILE` (T1a). `.local/bin/fzf-menu` is the dmenu replacement for keybinds (rows on stdin, choice on stdout, exit 1 = cancel; `-p`, `-m`, `--preview`, `--image`, `--index`, `--here`, any other fzf option passes through): it opens a `float.tui` ghostty, refocuses the previous window, closes the open menu on a second call, and keeps hidden **one-shot** menu terminals so a menu opens in about 40 ms (cold ghostty: about 0.4 s, the automatic fallback): `fzf-menu --server a|b` waits parked on its own special workspace (`special:menu-a` / `special:menu-b`, the `fzf-menu-server-a|b` window rules in `hyprland.lua`, matched by title), serves exactly ONE request and exits, so the menu window closes like any window (the hub does the same: popin + fade of the last frame, the then empty special workspace closes by itself through `misc:close_special_on_empty`, which `hyprland.lua` sets explicitly) instead of a workspace toggle that faded a blank terminal; fzf runs with `--no-clear` in window modes so that last frame is the menu itself (`--here` keeps clearing). 250 ms after a menu opened, `--spawn-standby` starts a standby terminal of the OTHER slot (`standby.lock`: at most one waits; it blocks on `server.lock` until the active one is done; the lock descriptors are closed for children, otherwise the standby would wait for itself), the client waits up to 0.5 s for `started` and up to 300 ms for a standby that is taking over (`wait_server`), `--server-start` / the cold path start slot a only when no server and no standby exist. **Hand-over protocol**: the server claims a request with an atomic `mkdir req/owner` and writes ITS OWN pid into `req/started`; a client that saw no `started` in 0.5 s takes that claim itself and goes cold (so a request is never served twice, the late server skips it); when that claim fails the server already owns the request (it may stall for seconds under load between `mkdir owner` and writing `started`), so the client never goes cold then: it waits for `started` or an answer while the process whose pid `server.pid` named AT THAT MOMENT lives (read once: a standby that takes over later does not extend the wait; bounded by `FZF_MENU_CLAIM_WAIT`, 30 s) and counts the request as cancelled when that process died; the server reports `finished` through an `<>` (O_RDWR) open of the `done` fifo, because a write-only open blocks for ever once the client has given up and closed its end; and while the menu is open it watches that pid: a menu window closed with `SUPER+W` (or a crash) ends the call as cancelled (status 1) instead of hanging, whoever serves the next request (an older server that writes an empty `started` keeps the old rule). Each slot has a lifetime lock (`slot-a.lock`, a second terminal of the same slot exits), the window lookup runs before a server becomes active, and the fifo / lock descriptors (3, 5-9) are closed in the menu subshell, the cold terminal and the background spawn, so an app started from a menu action can never keep `menu.lock` / `server.lock`. The window switcher hides the `fzf-menu-server-a|b` terminals. `--size normal|large` (60% x 65% or 85% x 85% of the monitor; `keymap menu` uses large): `server_show` shows the window with ONE `hyprctl eval` chunk (`hl.dispatch(...)` statements: plain `toggle_special`, or `set_prop no_anim 1`, toggle, `resize`, `center`, `set_prop no_anim unset` only when size or monitor differ from the target). If a menu still shows motion on close, add `no_anim = true` to the two window rules (comment in `hyprland.lua`; menus then vanish instantly). Diagnostic for the owner: `infrastructure/tests/fzf-menu/watch-anim.py SECONDS` (read-only event + geometry log). Tests: `infrastructure/tests/fzf-menu/run.sh [--quick]` (fake hyprctl, fake terminal in a private tmux; doctor `fzf-menu-tests`). An old live server keeps serving until it is restarted (hub > Fix > fzf-server), the protocol is compatible. `fzf-menu --self-test` drives the modal in a private tmux (doctor runs it). Every private tmux server of a test suite or tool (`tmux -L name`) removes its socket file after `kill-server` (which leaves it behind; `infrastructure/tests/tmux-sockets/run.sh` runs the suites with an empty `TMUX_TMPDIR` and checks, doctor `tmux-sockets` counts the dead ones). Image previews (clipboard, window switcher icons) use chafa through `.config/fzf/image-preview.sh`: fzf shows kitty graphics only as Unicode placeholders, so the script unwraps chafa's tmux-passthrough output (inside tmux it falls back to character cells). New menus: call `fzf-menu`, give NORMAL keys through `FZF_MENU_NORMAL_BINDS` and `--expect` Alt keys; never call `rofi -dmenu` (doctor checks).

### Hubs and window tools
- `hub` (`.config/hub/`, `SUPER+M`, tmux `prefix m`, zsh `hub`): fzf utility hub in a `float.tui` ghostty. Rows come from `actions.tsv` (+ `actions.d/*.tsv`; format in the header of `.config/hub/hub`) merged with every described bind from `hyprctl binds -j`; keybind rows are executable (below); toggles show live ON/OFF; rows whose command is not installed are hidden. `hub open` records the previously focused window (`$XDG_RUNTIME_DIR/hub/prev-window`) so window actions target it. Later stages append rows to `actions.tsv`.
- `scripts/window-menu.sh` (`SUPER+SHIFT+W`, fzf-menu): per-window actions with `address:` dispatchers; `--dry-run --do ID` prints the dispatcher. Extra entries come from executable files in `scripts/window-hooks/` (`# menu: Label` line; run as `hook ADDRESS`).
- `scripts/window-switcher.sh` (`SUPER+SHIFT+space`): fuzzy switcher over all windows. `scripts/safe-close.sh` (`SUPER+W`): double press within 1 s for the classes in `.config/hypr/protected-classes`. ### Dev environments (DEV-b: mise + envs)
**mise replaces direnv** (the hook, the package and the dead nvm lines are gone). `.config/zsh/mise.zsh` (sourced from `.zshrc` after the last PATH change) returns at once when mise is missing; humans get `mise activate zsh` from a cached init file (`~/.cache/zsh/mise-activate.zsh`, regenerated when the binary or the script is newer), agent and non-tty shells (`$CLAUDECODE`, no tty) get **shims** only (a snapshot never runs precmd, so `activate` would freeze a stale PATH). `DF_MISE_MODE=activate|chpwd|shims` (never a `MISE_*` name: mise reads those as settings; set it in `~/.zshrc.local`) moves humans to the cd-only hook (`chpwd`: the per-prompt `_mise_hook*` is removed) or to shims when `hook-env` costs too much per prompt. **Install on cd** is automatic and trusted-only: a chpwd hook notices a new or changed mise config, asks `mise ls --current --missing` (an untrusted `mise.toml` makes that fail, so nothing is installed) and runs `mise install` detached; the next prompt prints one line (log in `$XDG_RUNTIME_DIR/mise-auto/`); `DF_MISE_AUTOINSTALL=0` turns it off. The legacy version files (`.tool-versions`, `.nvmrc`, `.node-version`, `.python-version`) need no `mise trust`, so a fresh clone with one must not start an install by itself (a registry tool backed by an asdf/vfox plugin is third-party code): for them the hook only prints a hint line; the global config also sets `disable_backends = ["asdf", "vfox"]` (key unverified until G7). The global `.config/mise/config.toml` has **no `[tools]`**: outside a project pacman go/node/python and rustup stay in charge (Claude Code, Mason, npm -g CLIs, nvim untouched); projects pin in `.mise.toml` (or `.nvmrc` / `.node-version` / `.python-version`, enabled as idiomatic files); `trusted_config_paths` stays empty and trust is its own question: `envs trust` (also offered right after `envs bind` and, on a terminal, `envs init`) lists the config files, says that mise can run commands from them with the environment's secrets and that trust is path-based (a later `git pull` that edits the file is trusted too), and only then runs `mise trust`; bind, init and the first `envs run` never imply it and never re-trust silently (without trust, `mise exec` refuses the config with its own message). Whether mise's `paranoid` mode (hash-based trust) fits is a G7 check. Inside a project a pinned old node/python shadows the system one for npm -g CLIs and Mason LSPs: `cd ~` or `mise exec node@system`. Managed users (td, yc) get their own mise installs (the cli profile links `.config/mise`); no `/srv/mise-shared`, because td's agents run `mise use` themselves. Both packages come from `apply-system.sh --only install` (`mise usage`; `direnv` is in the remove list). `sysup` has a `mise` step after `go` (`plugins update`, `upgrade --yes`, `prune --yes`; skipped without mise) and starts the install run with `cd $HOME` plus `clean_project_env`: a terminal inside an activated project would otherwise leak the project's PATH (mise install dirs, shims), `MISE_ENV`, `__MISE_*` and its `[env]` (`GOBIN`, `NPM_CONFIG_PREFIX`) into `go install`, `npm -g` and `mise upgrade`; the `[env]` part is undone from mise's own record in `__MISE_DIFF` (format assumed as deflated JSON `{original, additions, deletions}`: verify on G7; an unreadable record is skipped, the PATH/`__MISE_*`/`MISE_ENV` cleanup always happens). `mise plugins update` pulls third-party plugin code that later runs inside `envs run` (with secrets): accepted.

**`envs`** (`.local/bin/envs`, one stdlib Python file, shebang the absolute `#!/usr/bin/python3 -I` so neither a project's pinned Python nor a `_.path` entry can run in its place, and a project pinning Python <= 3.10 cannot break it; header = usage) keeps **secret values only in the command**: `envs run -- CMD` (aliases `er CMD`, `ere ENV CMD`, `ert TASK` = `envs run -- mise run TASK`; a shell function such as `grun` cannot be wrapped) execs the command (`mise exec --` when the project has a mise config, `MISE_ENV=<env>` so `.mise.<env>.toml` applies; the child also gets `ENVS_PROJECT`, `ENVS_ENV`) with only the declared secrets added; no Python process stays alive holding them. **Files**: `.envs.toml` in the project root (committed, names only: `project`, `environments`, `default`, `protected`, `[secrets] NAME = "description"`; validated by `envs check`/every command: project `^[a-z0-9][a-z0-9._-]{0,62}$`, env names `^[a-z][a-z0-9_-]{0,31}$`, variable names plain identifiers, reserved `PATH HOME PYTHONPATH PYTHONHOME NODE_OPTIONS NODE_PATH BASH_ENV ENV ZDOTDIR GLIBC_TUNABLES GCONV_PATH PERL5OPT RUBYOPT GIT_DIR GIT_WORK_TREE BW_SESSION SSH_AUTH_SOCK XDG_* dirs ...` and the prefixes `MISE_ ENVS_ __MISE LD_ GIT_CONFIG VAULT_BW_` refused, a `default` that is protected (prod) refused, a name cannot be both a secret and a mise `[env]` key; our own line editor changes it and keeps comments and order, quoted keys are refused) and mise `[env]` for plain variables (`.mise.toml` for every environment, `.mise.<env>.toml` for one). **Values**: Bitwarden folder `Env/<project>` (the parent `Env` is created too), one **Secure Note per environment** named exactly like it (`dev`, `stage`, `prod`), one **hidden** custom field per secret; extra fields are reported by `envs check`/status and never injected. Reads go through rbw (`rbw list --raw`, `rbw get --raw ID`), writes through `vault-bw.py` (REST over the bw server: read-modify-write of the current item under `flock $XDG_RUNTIME_DIR/envs/write.lock`, then `refresh_rbw()`; folder rename/delete through `PUT`/`DELETE /object/folder/ID`). State: `~/.local/state/envs/{active,bindings}.tsv` (dir 0700, files 0600, atomic writes; a root path with a tab or newline is refused, it would forge rows). **Environment hygiene**: tools are resolved from `/usr/bin:/usr/local/bin:~/.local/bin` only, and `envs` sets its own `PATH` to exactly that (the user's PATH, hook variables and the original `XDG_*` values go back only to the final command, which also gets mise's log switches removed and `MISE_LOG_LEVEL=warn`); the state, runtime and config directories are the account's, whatever `XDG_STATE_HOME`, `XDG_RUNTIME_DIR`, `XDG_CONFIG_HOME` or `HOME` a project's `[env]` sets; `RBW_BIN`, `BW_BIN`, `PINENTRY_BIN`, `VAULT_BW_*` and `VAULT_RBW_CONF` are ignored (and `wl-copy` for `copy-value` and the pinentry are absolute paths: the secret or the master password goes to their stdin); git runs without `GIT_*` variables; `er`/`ere`/`ert` call `$HOME/.local/bin/envs`. This hardens the paths the review found; it cannot sandbox a trusted mise config, which is code (see trust above).
- **Commands** (`envs --help`): `init`, `bind`, `status [--json]`, `use [ENV] [--prod] [--for 60m]`, `run`, `set NAME [-e ENV | --all] [--plain] [--stdin] [--description]` (hidden prompt asked twice or `--stdin`; a value on the command line is refused), `unset`, `rename`, `copy SRC DST [--overwrite]`, `diff [A B]` (compared in memory, only verdicts printed), `env new|rename|delete`, `project rename|delete` (typed confirmation, items go to the Bitwarden trash), `import [FILE]` (dotenv parser; secrets -> the environment item, plain -> mise files; only a regular file inside the project root, a symlink or an outside file is refused (`.env -> ~/dotfiles/env.secret.sh` from a build step); an untracked file is shredded after a confirmation, a tracked one is kept with a rotate warning; `shred` is best effort on SSDs and journalling file systems, so rotate anything that was ever on disk), `export-example` (names only, never overwrites a foreign file), `copy-value NAME` (`wl-copy --sensitive`, cleared after 30 s), `convert NAME [--prod]` (secret <-> plain; the TUI `p`), `trust`, `check [--all]`. - **Guards**: **agents never get values**: every command except `status`, `check`, `diff`, `export-example` refuses when an ancestor process is `claude`/`codex`/`gemini`/`claude-agent-acp`/`codex-acp` (`/proc/PID/comm` up to pid 1, or an interpreter running such a script, matched by the script's basename or by path component such as `node .../@openai/codex/bin/codex.js` or `.../claude-code/cli.js`) or `$CLAUDECODE` is set; the TUI's internal `_preview` is refused too. **Binding**: the first secret use in a checkout asks `Bind <root> to Bitwarden folder Env/<project>? [y/N]` (key = realpath of the git common dir plus `//relative/path` for a root below the top level, so every worktree of one repo shares it and two projects of one monorepo bind separately; no git = the root). A `.git` FILE counts only for a real linked worktree (the gitdir holds `commondir` and a `gitdir` back-link that resolves to that very file); a `.git` file or symlink of an unpacked archive that points at a bound clone's `.git` borrows nothing and asks. git itself is never asked for the key (it trusts the same file); a changed `project =` for a bound root is refused until `envs bind`, so a cloned repo cannot name another project and pull its secrets. **Protected environments** (`prod`, `production`, plus `protected = [...]`): `envs use prod` needs `--prod` or the typed name and expires after 60 minutes (`--for 2h`, max 8 h), `envs run` in one needs `--prod` or a `[y/N]` on a tty, and every protected run logs one journald line (`logger -t envs`: project, env, basename of argv[0], number of variables; never values or arguments). - **Threat model (honest) and what the fence is**: envs prevents LEAKS (shell environment, agent context, argv/ps, history, logs, notifications, disk), it is not isolation. The agent refusal, the binding prompt and the `[y/N]` / typed confirmations of `prod` stop accidents, naive prompt injection and a cloned or downloaded repo that names someone else's project; they do not stop a determined local process of the same uid. What cannot be fixed here: (a) any process of the same uid can read `/proc/PID/environ` of a running `envs run` child and of the TUI's fzf (so the per-run `FZF_API_KEY` and reveal flag path are not secret from it; Yama only restricts attach), and while rbw is unlocked it can run `rbw get` itself; (b) td's own rbw holds the owner's whole vault while unlocked and td runs AI agents, so everything in that vault is readable by td's agents (folder filtering is cosmetic; a separate Bitwarden account or organisation collection for td/yc is the real fix, decide before B1; `bw-setup` therefore gives a managed user a one-hour `lock_timeout`, the owner one year); (c) the agent refusal is ancestry based: a process that detaches from its agent (`setsid -f`, reparent to systemd, `tmux new-window`, `systemd-run --user`) is not recognised (tested as a known limit); (d) every confirmation is a terminal prompt, and any local process can answer a prompt through a pty (`printf y | script -qec 'envs bind' /dev/null`), so `bind` and the prod `[y/N]` are speed bumps for a human, not authentication (a GUI pinentry confirm would be the next step); (e) a trusted project's `[env]` and mise templates are code that runs with the secrets present: mise trust is the only gate (path-based, see above), and a parent-directory or global mise `[env]` that sets a declared secret's name overrides the injected value (envs warns on stderr and in `check`); (f) the names-only commands (`status`, `check`, `diff`) need no binding and show, for any directory that names a project, which names are set and whether two environments differ (never a value), also to agents. ### Telegram sending (M1-send)
Agents can ask to send a Telegram message; nothing leaves without the owner's confirmation of that exact message. Off by default.
- **Path**: agent -> gateway server `telegram-send` (`.config/mcp/telegram-send.py`, stdio, owner uid, no secret, no Telegram code; tools `send_message(chat, text, reply_to, account)` and `status`, toolFilter allow exactly those two; the gateway leaves it out of the effective config until `tgconfirm.service` or its socket exists) -> `/run/tgconfirm/req.sock` -> the **tgconfirm broker** (`infrastructure/mcp/confirm/broker.py`, system service, managed service user `tgconfirm`, mode 0666 socket + `SO_PEERCRED` owner-uid check) -> `POST /x-send` of telegram-mcp (`serve.py`, user `aimcp`, its own send token and send allowlist, same Telethon client; never an MCP tool, `check_env()` still demands exactly `read-only`). Answers: `sent (id N)`, `cancelled`, `timeout`, `disabled`, `rejected: <reason>`, or "outcome unknown, check the chat" when `telegram-send.py` stopped waiting (it never claims that nothing was sent then). After a sent message `telegram-send.py` (it runs in the owner's session, so it has the notification bus) shows a "Sent to NAME" notification.
- **Per message**: the broker resolves the chat, then opens a popup (`popup.py` in ghostty as `tgconfirm`, class `float.confirm`: float, center, pin, `stay_focused`, `no_screen_share`) with the account, recipient, chat id, reply preview and the full text (control, zero-width and bidi characters shown as `<U+XXXX>`). **Resolve only against the sealed send list**: a numeric id is checked locally, a title or `@username` is matched against the cached names of the allowlisted chats only (fetched once per 10 min); any other chat is the same 403 without a Telegram lookup, so there is no FLOOD_WAIT risk and no username-existence oracle.
- **Popup rules** (`popup.py`, layout is a pure function with tests): the text is wrapped to the width that is really drawn and clipped by display width (wide and combining characters counted like a terminal), scrollable (`j k d u`, arrows, PageUp/PageDown); the code (a random two-key code, 1 of ~400, ua/ru twins count) appears only after the end of the text was on screen, in a random 3-row box at a random row and column that the text flows around, with the recipient repeated inside it, and is drawn only in a window between 60x18 and 400x120 cells; any size change after the code was shown cancels. Guard: the 0.7 s guard starts at the terminal's first focus-in report (mode 1004; no report = 2 s after the first frame), every key that arrives during the guard and every resize restarts it, and a focus-out before the code is complete cancels. Any wrong key, Esc or `q` cancels (one shot per message), 60 s without an answer is a timeout; the broker never learns the code.
- **Compositor trust** (the owner, so any agent, can plant a `wayland-N` or strip the ACL, and `tgconfirm` has only `x` on `/run/user/UID`): the broker does not list the directory. It connects to `wayland-0..9`, reads the server pid with `SO_PEERCRED` and accepts a socket only when that process is named `Hyprland`, runs as the owner, and descends through `start-hyprland` (optionally via the login shell `hypr-login` execs) from the LEADER of the active seat0 logind session (logind's root-owned runtime files). Two different passing compositors, a nested test compositor, or no match = refused. The connected fd itself goes to ghostty as `WAYLAND_SOCKET` (no `WAYLAND_DISPLAY`, so it fails closed and nothing can be swapped between check and use). doctor `mcp-send-wayland` runs the same check against the live session (`broker.py --check-wayland`).
- **Budgets and limits**: one request is bounded by a broker budget of 115 s (lock wait 10, resolve 12, popup 65 = 60 + 5 s grace, send 25) < `telegram-send.py` wait 130 s < gateway timeout 150 s, so an agent never hears "timeout" for a message still on its way; a client that hangs up closes a pending popup and nothing is sent. Rate limits: 5 popups / 10 min (one popup at a time, a locked screen refuses), 20 requests / 10 min at the broker (every request counts, popup or not, checked before any resolve), 30 lookups / 10 min and 5 sends / 10 min at `/x-send`. Journald audit (`tgconfirm:` / `telegram-send:` lines: account, chat id, length, sha256 prefix, result; never the text).
- **Switch**: `mcp-telegram-send on|off|toggle|status` (hub toggle row `tg-send`, leader `x m`, waybar `tgsend` glyph with the minutes left in the toggles summary and drawer; hidden while no broker runs). Enabling goes through the broker and shows its own popup, so an agent cannot switch it on silently; 60 minutes by default (`--ttl`, broker cap 120), the broker expiry plus a transient `mcp-telegram-send-off` user timer switch it off with a notification; turning it off needs no confirmation.
- **Secrets and setup**: the send token exists only as TPM2 credentials of `telegram-mcp` and `tgconfirm` (`/etc/credstore.encrypted/{telegram-mcp,tgconfirm}.send_token`). `creds-install` (root helper) always generates it itself (`--ensure-send-token`, `--rotate-send-token`; a `send_token` on stdin is rejected in every case), so it is never in Bitwarden, in a file `skalse` can read, in argv or in this repo. The helper also keeps the sealed `send_allowlist` a subset of the read `allowlist` by itself whenever the read list changes (a tampered Bitwarden copy cannot widen it) and checks a `send_allowlist` on stdin against the new or sealed read list; `--print-send-allowlist` prints the sealed list. `mcp-telegram-setup send-chats [--account NAME]` starts from the SEALED list (read through the root helper), warns when the Bitwarden record differs, opens the same checkbox picker, prints the summary (`Adding` / `Removing` with title, kind, id, then the final list) and asks `Seal this send list? [y/N]` (an explicit `y`) before anything is written; no change = `No change.`; the Bitwarden `send_allowlist` field only follows the sealed list afterwards. `chats` (read list) no longer seals a send list at all. Only `main` until M1b (several accounts = one telegram-mcp instance and credential set per account, the broker maps `account` to a port). The root part is `sudo ./apply-system.sh --only users,mcp`.
- **Runtime dir ACL** (`usr clipboard-acl`, also for `td`): the `wayland` / `clipboard` users get `x` on `$XDG_RUNTIME_DIR`, `rw` only on the Wayland socket and an explicit empty named entry (deny) on everything else reachable: every socket up to depth 4 (`pipewire-0`, `bus`, `systemd/io.systemd.Manager`, `pulse/native`, ...), every first-level directory and file; a default ACL on the runtime dir makes new entries start denied (rwx for group/other/mask so creators' modes stay). `infrastructure/users/acl-reach.py` and doctor `mcp-send-route` apply the kernel's rule (named entry limited by the mask, else the OTHER bits) so a 0666 socket or a 0644 file without a named entry counts as reachable. **After a compositor restart** the new `wayland-N` inherits `u:tgconfirm:---`, so the popup would fail until the ACL is re-applied: the Hyprland autostart runs `usr clipboard-acl` once per compositor instance (the autostart marker is per `HYPRLAND_INSTANCE_SIGNATURE`), which covers every compositor restart. There is deliberately no watcher: a `wayland-acl.path` unit (`PathChanged=%t`, inotify on the whole runtime dir) fired on every change in `/run/user/UID`, hit `start-limit-hit` and left a failed user unit, so it was removed (FIX-wayland-acl). A `wayland-N` created by another route (a nested compositor started by hand) stays denied until `usr clipboard-acl` is run by hand; the broker's own compositor check is independent of the ACL. doctor `mcp-send-route` checks what the ACL reaches.
- **Threat model (honest)**: agents run as `skalse`, read every 0600 file of `skalse` and can inject keys with `wtype`/`wlrctl`/`hyprd`/`hyprctl eval`, so the popup cannot be unforgeable by itself. Defences: the send token is unreadable for `skalse`; the code is per message, random, drawn late and in a random place; the popup is invisible to screen capture; the broker talks only to the verified session compositor; `telegram-send` is registered for Claude Code only (`mcp-add` removes it from Codex); rate limits, audit, auto-off and the server-side send allowlist. `mcp-guard` (Claude Code `permissions.deny` rules in `~/.claude/settings.json`; backup, `--dry-run`, `--remove`, `--check`; doctor INFO until run) is **best effort, not a defence layer**: Claude Code matches command prefixes, so it covers `wtype`, `wlrctl`, `ydotool`, `dotool`, `hyprd`, `hyprctl eval|dispatch` (with `-j -r -q` flags, `-i/-b/-c`), `grim`, `wf-recorder`, `wl-screenrec` and the repo's capture, paste, typing, pointer, window-menu, ai-ask, edit-anywhere and `2fa-import` scripts, each by bare name, `~/` path, `$HOME` path and absolute path, and a determined agent can still wrap a command (`bash -c`, `env`, a script it writes, python with a Wayland library). What protects a message is the popup and the owner reading the recipient and the text. **Residual risks**: a move without a resize is not detected (a pointer-capable agent can slide the window partly off screen); pid-based identity has a theoretical pid-reuse race between the compositor check and the connect (the fd is the verified connection, which narrows it to the check itself); Codex runs with `--dangerously-bypass-approvals-and-sandbox` and, although `telegram-send` is not registered for it, can still reach the gateway route with the gateway token (not secret from `skalse`), and any agent that edits the Hyprland config or guesses the code in its one shot can get out one message per popup. Every message still needs the popup code; the defences target prompt injection from untrusted chat text, the realistic threat. Kill switch: Telegram > Settings > Devices (the session is still named "telegram-mcp (AI, read-only)" from before sending existed).

### Shortcut reference (keymap)
One generator, never hand-kept: `.config/keymap/keymap.py` (stdlib Python, wrapper `.local/bin/keymap`) collects every shortcut into `~/.cache/keymap/keymap.json` (rows: block, keys, description, source, optional context/note) and every view comes out of that file. There is no sshd; the firewall locks out nothing local. **Docker**: ufw and Docker both manage iptables. Container traffic to the internet keeps working (Docker's FORWARD rules apply after ufw's chains, which pass new connections through), and the host reaches published ports. Published ports bypass ufw's INPUT rules (DNAT traffic is forwarded, not input), so a port published on `0.0.0.0` stays open to the LAN despite the firewall: publish on `127.0.0.1:` (all current ones are) or filter in the `DOCKER-USER` chain; `net-exposure` flags a `docker-proxy` listener on a non-loopback address. A container that must reach a service of the host (`host.docker.internal`, the bridge gateway `172.x.0.1`) is blocked by default-deny INPUT: no compose file under `~/job` does that, and a container with `network_mode: host` (ch-ui, `td-clickhouse-ui`, `*:3488`) listens on the host itself, so ufw does cover it; the commented example in `ufw-rules.conf` shows the bridge allow (`allow in on docker0 ...`, `br-+` for compose networks). Stale hand-added rules (`1080/tcp` and `3128/tcp` were in `user.rules` before) are never removed silently: the section warns and doctor fails until they are deleted (`sudo ufw status numbered`, `sudo ufw delete N`) or added to `ufw-rules.conf`. **LLMNR off**: `/etc/systemd/resolved.conf.d/10-no-llmnr.conf` (`LLMNR=no`, `systemctl try-reload-or-restart systemd-resolved` only when it changed); MulticastDNS stays on (`.local` lookups, UDP 5353, allowlisted; with the firewall only the multicast group gets through). **v2rayA on loopback**: drop-in `/etc/systemd/system/v2raya.service.d/10-loopback.conf` with `Environment=V2RAYA_ADDRESS=127.0.0.1:2017` (the package's own variable, see `/etc/default/v2raya`; the packaged file is not edited), the unit is restarted only when it runs. The camoufox gateway (`~/job/youtube/skills/flow-render/scripts/camoufox_gateway.py`, user unit `camoufox-gateway`, not in this repo) defaults to `HOST=127.0.0.1` now, because every client (`flowpipe`, `flow_cli.py`, `run_out3.py`, the docs) uses `http://127.0.0.1:8788`; it takes effect on `systemctl --user restart camoufox-gateway`. **doctor `net-exposure`**: INFO until the section ran, then FAIL on a firewall that is not enabled/active/default-deny/IPv6, a drop-in that differs, an `ss -lntu` listener on a non-loopback address that `infrastructure/net/listeners.allow` does not list (TCP LISTEN and UDP below the ephemeral range; the list holds only `tcp 3488` ch-ui and `udp 5353` mDNS, each with its reason) and a stale ufw rule; the rule set itself needs root (`sudo ufw status verbose`). Logic in `infrastructure/net/exposure-check.sh`, tests `infrastructure/tests/net/run.sh` (doctor `net-tests`).

## AI agent cockpit (Neovim + tmux)

`install.sh` is idempotent and user-agnostic: no usernames, home paths or e-mails are hardcoded.
Git identity lives in `~/.gitconfig.local` (written by `install.sh`, included from `.gitconfig`).
After `stow .` it runs `.config/nvim/scripts/bootstrap.lua` headless, which restores plugins from
`lazy-lock.json`, installs Mason tools and treesitter parsers, and writes the agent hooks
(`:AgentDashInstallHooks`) into `~/.claude/settings.json` / `~/.codex/hooks.json` with backups.

Neovim side (`lua/plugins/ai/*.lua`, all keys under `<leader>a`):
- `sidekick.nvim` — Claude/Codex/Gemini CLIs in persistent tmux windows, context prompts
- `agentic.nvim` — ACP quick chat (`claude-agent-acp`, `codex-acp`)
- `codediff.nvim` + `review.nvim` — post-hoc review, comments sent back to the agent
- MCP: no nvim plugin; the agents (Claude Code, Codex, the ACP adapters) use the local MCP gateway, see "MCP gateway and agents" above (mcphub.nvim and the unauthenticated mcp-hub on `*:37373` were removed in M1)
- `lua/agentdash/` — custom dashboard of sessions/subagents/tasks fed by agent hooks (`:AgentDash`, statusline segment)
- `workmux` (`.config/workmux/config.yaml`) — git worktree + tmux window per agent task, `<leader>aw*`

Installing new nvim plugins: use `nvim --headless "+Lazy! install" +qa`, never `Lazy sync`/`clean`
(they bump every pinned commit in `lazy-lock.json`).
