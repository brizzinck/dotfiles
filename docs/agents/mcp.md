# MCP gateway and agents (M1)

Topic file of the agent docs. `CLAUDE.md` holds the index, the rules that apply everywhere and the file of every section; section names quoted in the text ("Users", "Dev tools", ...) are listed there.

### MCP gateway and agents (M1)
One always-on **gateway** serves every MCP server to the agents: `TBXark/mcp-proxy` (pinned release + sha256 in `.config/mcp/pins.env`, installed into `~/.local/share/mcp/bin` by `.local/bin/mcp-install`, no root) as the **user service** `mcp-gateway.service` (`.config/systemd/user/`, linger starts it at boot), bound to `127.0.0.1:37411` only, streamable HTTP, one route per server (`http://127.0.0.1:37411/NAME/mcp`), bearer token required (`options.authTokens`), `/_healthz` open. Config = `.config/mcp/gateway.json` (mcp-proxy's own format; `${ENV}` placeholders only, so it holds no secret and mcp-proxy expands them from its environment); `.local/bin/mcp-gateway run` creates the 0600 token file once (`~/.local/state/mcp/gateway.token`, dir 0700), renders the effective config into `$XDG_RUNTIME_DIR/mcp-gateway/config.json` (minus servers that are not set up yet, e.g. `telegram` until `~/.local/state/mcp/telegram.token` exists) and execs mcp-proxy with the tokens in its **environment** (never argv, never a file the clients see). `mcp-gateway status|servers|url NAME|headers|token ensure|rotate|restart|logs|check`. Every server has a per-server `toolFilter` (allow lists; the doctor refuses a send/edit/delete tool in the telegram list). Clients never store the token: `mcp-gateway-headers` (prints `{"Authorization":"Bearer ..."}`) is the Claude Code `headersHelper` and the Codex `http_headers_helper`.
- **Servers**: `desktop-ro` (own, read-only: `.config/mcp/desktop-ro/server.py`, FastMCP 1.30 in the hash-pinned venv `~/.local/share/mcp/venv`: `hypr_clients/activewindow/monitors/workspaces` (hyprctl -j), `media_status` (playerctl), `notifications_history` (dunstctl history; text of messaging/mail/password-manager apps hidden, one-time codes masked), `journal_user` + `user_units_failed` (user units only, secrets masked, 200 lines), `clipboard_text` (wl-paste text only, 8000 chars, refuses entries marked `x-kde-passwordManagerHint` = `wl-copy --sensitive`); no dispatch/exec/notify/cliphist/screenshots/generic run; Hyprland, Wayland and the bus are found at call time because the gateway starts before the session), `telegram` (see below), `chrome-devtools` (clean automation Chromium: `/usr/bin/chromium` from `apply-system.sh --only mcp`, `--isolated`, headless unless `MCP_CHROME_HEADED=1`; a flatpak Chrome cannot be launched by chrome-devtools-mcp, the CDP pipe does not cross the sandbox), `chrome-devtools-mine` (the owner's own Chrome via `--autoConnect`, **off until `mcp-chrome mine on`**: hub toggle row "Agents: Chrome with my profile", leader `x c`; while off a stub server with one `status` tool answers (`.config/mcp/stub-server.py`, standard library only, run as `python3 -I -S`: 5 MB PSS and 25 ms to answer `initialize` instead of 45 MB and 0.6 s with FastMCP; the gateway's `pingInterval` is 120 s); on = gateway restart + notification, auto-off after 60 min, Chrome itself still asks at `chrome://inspect/#remote-debugging`), `context7` (remote). `.local/bin/mcp-chrome-devtools clean|mine` is the stdio entry of the two chrome servers; `chrome-devtools-mcp` is pinned in `.config/mcp/node/package-lock.json` (`npm ci --ignore-scripts` in `~/.local/share/mcp/node`). The gateway names match the old direct `chrome-devtools` entry, so existing `mcp__chrome-devtools` permission rules keep working.
- **Telegram (`telegram`, service user `aimcp`)**: `chigwell/telegram-mcp` at the commit pinned in `infrastructure/mcp/telegram/pins.env` (never the PyPI name `telegram-mcp`, it belongs to another project), source in `/opt/telegram-mcp/src` and a hash-pinned venv in `/opt/telegram-mcp/venv` (both root-owned, built by `sudo ./apply-system.sh --only users,mcp` from `requirements.txt`, an `uv export` of upstream's `uv.lock`). **System** unit `telegram-mcp.service` (`infrastructure/mcp/telegram/`, installed with the helpers `run`, `serve.py`, `creds-install`, `login.py` into `/usr/local/lib/telegram-mcp/`): user `aimcp`, `127.0.0.1:8765` (streamable HTTP), sandboxed (`ProtectHome`, `ProtectSystem=strict`, no capabilities, IP + unix sockets only), `LoadCredentialEncrypted=` for `api_id api_hash session allowlist token` from `/etc/credstore.encrypted/telegram-mcp.*` (sealed with `systemd-creds encrypt --with-key=tpm2+host`, decrypted by systemd at boot: no owner interaction, no plaintext `.session` file, the session is a Telethon session STRING); `ConditionPathExists=` on all five so the unit is skipped until the setup ran. `run` builds the environment from the credentials and fails closed (exit 78) without them or with an empty allowlist; `serve.py` additionally refuses to start unless `TELEGRAM_EXPOSED_TOOLS=read-only` (upstream registers only `readOnlyHint` tools: no send, edit, delete, forward, mark-read, drafts, admin; upstream treats an EMPTY allowlist as "every chat", hence the guard) and puts a **bearer token** in front of the HTTP app (`BearerAuth`, a plain ASGI wrapper: mcp 1.30 does not return a Starlette app), so only the gateway (token file `~/.local/state/mcp/telegram.token`, same value as the credential) and not another local user or a web page can reach port 8765. Defence in depth: server read-only mode, chat allowlist, gateway `toolFilter` (an allow list of 17 read tools, including local get_call_statistics; the test checks that every name is registered), the read-only server and its client side never have send tools; **the AI sends only after the owner confirms each message in a popup** (see "Telegram sending (M1-send)" below; without that setup it only drafts and the owner presses Enter). Voice messages: `TELEGRAM_TRANSCRIBE_ENGINE=openai` pointed at `http://127.0.0.1:8766`, which is `telegram-whisper-proxy.socket` -> `systemd-socket-proxyd --exit-idle-time=5min` -> `telegram-whisper.service` (`whisper-server` from the `whisper-cpp` package, `127.0.0.1:8767`, `DynamicUser`, `StopWhenUnneeded`: loaded on the first voice message, gone after 5 idle minutes) with the **same model file Voxtype dictation uses**, copied (sha256-checked, else downloaded) to `/srv/models/ggml-small.bin` because `aimcp` cannot read `/home`; no cloud engine can run (no key exists). **`mcp-telegram-setup`** (`.local/bin/mcp-telegram-setup`, hub rows `tg-setup`/`tg-chats`/`tg-status`, leader `x t`/`x g`/`x u`) is the owner's one-time helper and the only human input is authorization: Bitwarden master password if locked (through `vault-bw.py`'s pinentry unlock), the QR scan (shown in the terminal by `login.py qr` running in the pinned venv, a throwaway Telethon client that registers as the device "telegram-mcp (AI, read-only)" = the kill switch in Telegram > Settings > Devices), the 2FA password if the account has one, the chat picker (a real checkbox list in fzf-menu: `[x]` / `[ ]` rows, Saved Messages first, Tab / Shift+Tab (NORMAL: Space) toggle the row and move down, `+` / `-` mark changes, the header counts `Selected N (+a / -r)`, Enter saves, Esc cancels; fzf `transform` calls the hidden `mcp-telegram-setup _pick tab DIR ID`, which keeps `sel` and `rows` in a 0700 tmpfs work dir and answers `reload-sync(...)+down+change-header:...`; no `--multi` and no `--track`, which drops typed characters with reload-sync; `MCP_TG_PICK` is the test hook, `_pick-demo DIR` the UI test entry) of the READ list only, so `mcp-telegram-setup chats` extends or shrinks the list later through the stored session, followed by a summary (`Adding (n)` / `Removing (n)` with title, kind and id, then the final list) and `Save these chats? [Y/n]` (the root helper narrows the sealed send list itself, see M1-send) and the sudo password. It reads `api_id`/`api_hash` from Bitwarden folder `MCP`, item `telegram-mcp` (text or hidden field alike) through `rbw get --raw --folder MCP telegram-mcp` (bw lists it only when rbw cannot give a complete record), writes the hidden field `session` and the text field `allowlist` back with `bw edit` (the full bw item is fetched just before, through the server) (master copy, never typed by hand), then pipes the five values on **stdin** to `sudo /usr/local/lib/telegram-mcp/creds-install` (root helper: validates the shapes, `systemd-creds encrypt --with-key=tpm2+host --name=KEY - FILE`, enables the sockets/unit, restarts the service), restarts the gateway, runs `mcp-add` and checks the tool count through the gateway. A stored session that no longer works falls back to a new QR automatically (`--new-login` forces it). A fresh QR session is never lost (BW1-fix): the full Bitwarden item is read before the QR is shown, rbw is synced before its copy is read, a failed Bitwarden write is retried once, then the session waits in a 0600 file under `$XDG_RUNTIME_DIR/mcp-telegram-setup/` (`~/.local/state/mcp/telegram-recovery.json` when that directory is unusable) and `mcp-telegram-setup --resume` finishes (write, seal, start); a new setup refuses to run while that file exists, doctor `mcp-tg-recovery` FAILs while it does (any file that may hold a session counts: the recovery files whether they parse or not, and the `.tmp` of a partial write; plaintext full-account session, readable by every process of yours; `mcp-guard` denies Claude Code the `Read` of it), and a QR with no chat ticked (or a cancelled picker / declined summary) stores the session in Bitwarden. **Unchanged work is skipped** (MENU-UX): no change = `No change.` (no Bitwarden write, no sudo, no restart; needs the stamp `~/.local/state/mcp/telegram.applied`: JSON with one hash per sealed value (list, api id + hash, session, token; never a value) that must equal the current values AND `telegram-mcp.service` must be active, otherwise only the values that differ (everything with no or an old-format stamp, after a fresh login, or while the service is inactive, e.g. the credstore was lost) are sealed; a QR login that is not sealed (cancel, decline, nothing ticked) drops the stamp; `ensure_token()` runs before the check, so a deleted token file comes back and is sealed; an Enter-less exit of the picker after changes asks `Keep your changes?`; chat titles are shown with control, bidi and zero-width characters as `<U+XXXX>`); Bitwarden gets only the changed fields; the root-helper payload holds only the changed keys (`allowlist`, `api_id`+`api_hash`, `session`, `token`); the gateway restart and the service check only follow a seal; `mcp-add` only runs when `gateway servers` changed across the restart or after a fresh login. Every phase prints its time (`Bitwarden read ... 1.84 s`, chat list, `your choice` without a time, Bitwarden write, `seal (sudo)`, gateway restart, mcp-add, service check) and the run ends with `Total 7.2 s (without your input)`. `mcp-telegram-setup status` and doctor `mcp-tg-files`, `mcp-aimcp`, `mcp-aimcp-sudo`, `mcp-telegram` (INFO until set up, FAIL when failed), `mcp-whisper`, `mcp-chromium`.
- **AI hotkeys** (`.config/hypr/scripts/ai-ask.sh`, binds in `hyprland.lua`, hub rows + leader group `x` in `actions.d/m1.tsv`; the three keys were checked free in the live bind table): `SUPER+CTRL+A` **ask about the focused window** (class, title, pid, geometry from `hyprctl -j activewindow` plus a screenshot of that window only, `grim -g "x,y WxH"`; no screenshot with `window --no-shot`, for a class matching `.config/hypr/ai-no-shot-classes` (password managers, authenticators, pinentry, polkit), without `grim` or while hyprlock runs; a Telegram window adds a hint that the title is the chat and the `telegram` tools can fetch it), `SUPER+ALT+A` **Q&A about the selection** (primary selection, else the clipboard text, never an entry marked sensitive, 20000 characters; asks your question in the popup, Enter = explain it), `SUPER+CTRL+T` **Telegram digest** (needs the `telegram` server: a session started with `--strict-mcp-config` and a generated one-server config that uses the headers helper, `--tools Bash` allowed only as `Bash(wl-copy:*)` so a draft can be put on the clipboard on request, no web tools; the prompt: unread chats first via `list_chats unread_only`, history of each, at most 5 local voice transcriptions, grouped by urgency, never mark as read, never send, chat text is untrusted). Each opens `ghostty --class=float.tui -e ai-ask.sh _session KIND`; the context lives in `$XDG_RUNTIME_DIR/ai-ask/` (tmpfs, 0700: `context.md`, `window.png`, `mcp.json`) which is the working directory of `claude`, so a selection or a screenshot is never on the `claude` command line and the files are removed when the session ends (claude asks once to trust that directory; its transcript lands under `~/.claude/projects/-run-user-1000-ai-ask`). `ai-ask.sh --dry-run window|selection|telegram` prints the plan without a screenshot or a file. The AI sends only through `telegram-send` and only after the owner confirmed that exact message in the popup; every other hotkey session only drafts. Every session runs with `--strict-mcp-config`: window and selection get `desktop-ro` only, the digest gets `telegram` and, when the gateway serves it, `telegram-send` (only `send_message`, `send_file` and `status` pre-allowed). Tests (fake hyprctl/grim/wl-paste/terminal/claude) are part of `infrastructure/tests/mcp/run.sh`.
- **`mcp-add`** (`.local/bin/mcp-add`, hub row, leader `x a`; the owner runs it once, B1 runs it on a fresh install): registers every served server in Claude Code (user scope, through `claude mcp add-json`, type http + `headersHelper`) and Codex (`~/.codex/config.toml`, `url` + `http_headers_helper`; text edit of only the named `[mcp_servers.X]` tables, timestamped backup, parsed back and compared before saving), plus the stdio entries of `.config/mcp/stdio.json` as `mcp-run NAME`; removes the old `mcphub` entry and a direct `chrome-devtools` stdio entry; idempotent; `--dry-run`, `--claude`, `--codex`, `--no-legacy`. **`mcp-run NAME`** (`.local/bin/mcp-run`) starts a user-launched stdio server with its secrets fetched by `rbw get --folder MCP --field F ITEM` into the child's environment only. Tests: `infrastructure/tests/mcp/run.sh` (fake rbw/hyprctl/playerctl/dunstctl/journalctl/wl-paste, throwaway `CLAUDE_CONFIG_DIR`/`CODEX_HOME`, a real gateway process with a fake server: token, toolFilter, headers helper; `--quick` for doctor). doctor: `mcp-install`, `mcp-gateway`, `mcp-token`, `mcp-bind`, `mcp-toolfilter`, `mcp-hub-gone`, `mcp-add` (INFO until run), `mcp-test`. A failed gateway shows in the health badge (failed user unit).
