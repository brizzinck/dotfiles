# Launcher and menus (rofi, fzf-menu)

Topic file of the agent docs. `CLAUDE.md` holds the index, the rules that apply everywhere and the file of every section; section names quoted in the text ("Users", "Dev tools", ...) are listed there.

### Launcher
**rofi** is only the app launcher (`$menu`, `SUPER+space`; `.config/rofi/`): it has no modes, so it gets the list grammar as far as rofi allows (`Ctrl+j/k` move, `Ctrl+d/u` page, `Esc` cancel, Cyrillic twins generated from `ROFI_OVERRIDES` in `layout.py`). wofi stays installed and is themed, but nothing binds it.

**Every other menu is the shared modal fzf** (V1b): `.config/fzf/vimfzf.sh` (sourced by scripts: `vimfzf ARGS`, `VF_PROMPT`, extra NORMAL-mode letters through `VF_NORMAL_BINDS` / the env `FZF_MENU_NORMAL_BINDS`) is a Telescope-like list: it opens in INSERT (typing filters, `Ctrl+j/k n/p`, `Ctrl+d/u`), `Esc` is NORMAL (`j/k g/G`, `i a /` back to INSERT, `q`/`Esc` quit; every other printable key is ignored; the mode tag `[I]`/`[N]` is in the prompt), ua/ru twins come from `lk_fzf_bind`, colours from `FZF_DEFAULT_OPTS_FILE` (T1a). `.local/bin/fzf-menu` is the dmenu replacement for keybinds (rows on stdin, choice on stdout, exit 1 = cancel; `-p`, `-m`, `--preview`, `--image`, `--index`, `--here`, any other fzf option passes through): it opens a `float.tui` ghostty, refocuses the previous window, closes the open menu on a second call (only while that menu is VISIBLE), and keeps hidden **one-shot** menu terminals so a menu opens in about 40 ms (cold ghostty: about 0.4 s, the automatic fallback): `fzf-menu --server a|b` waits parked on its own special workspace (`special:menu-a` / `special:menu-b`, the `fzf-menu-server-a|b` window rules in `hyprland.lua`, matched by title), serves exactly ONE request and exits, so the menu window closes like any window (the hub does the same: popin + fade of the last frame, the then empty special workspace closes by itself through `misc:close_special_on_empty`, which `hyprland.lua` sets explicitly) instead of a workspace toggle that faded a blank terminal; fzf runs with `--no-clear` in window modes so that last frame is the menu itself (`--here` keeps clearing). A server that has just become active and idle starts a standby terminal of the OTHER slot (`spawn_standby`; `standby.lock`: at most one waits; it blocks on `server.lock` until the active one is done; the lock descriptors are closed for children, otherwise the standby would wait for itself). **Ordering rule (FIX-MENU2, live bug)**: Hyprland hides the special workspace a monitor shows when a window is mapped on a special workspace that does not exist yet (the standby's own, destroyed while empty; seen in the socket2 log: `openwindow ... special:menu-b` then `activespecial>>,eDP-1` 20 ms later), so a standby is NEVER started while a menu is shown (it used to start 250 ms after a menu opened: every hot menu, e.g. the waybar volume right click, vanished about half a second later); `standby.spawning` (time in ms) marks a standby on its way, the standby removes it once its window is mapped and parked (a mark older than 1.5 s is ignored), and a server that got a request waits at most 0.6 s for it before `server_show` (a menu requested right after another one then takes about a ghostty start instead of 40 ms); `--spawn-standby` stays only for servers of an older version, the client waits up to 0.5 s for `started` and up to 300 ms for a standby that is taking over (`wait_server`), `--server-start` / the cold path start slot a only when no server and no standby exist. **Hand-over protocol**: the server claims a request with an atomic `mkdir req/owner` and writes ITS OWN pid into `req/started`; a client that saw no `started` in 0.5 s takes that claim itself and goes cold (so a request is never served twice, the late server skips it); when that claim fails the server already owns the request (it may stall for seconds under load between `mkdir owner` and writing `started`), so the client never goes cold then: it waits for `started` or an answer while the process whose pid `server.pid` named AT THAT MOMENT lives (read once: a standby that takes over later does not extend the wait; bounded by `FZF_MENU_CLAIM_WAIT`, 30 s) and counts the request as cancelled when that process died; the server reports `finished` through an `<>` (O_RDWR) open of the `done` fifo, because a write-only open blocks for ever once the client has given up and closed its end; and while the menu is open it watches that pid: a menu window closed with `SUPER+W` (or a crash) ends the call as cancelled (status 1) instead of hanging, whoever serves the next request (an older server that writes an empty `started` keeps the old rule). Each slot has a lifetime lock (`slot-a.lock`, a second terminal of the same slot exits), the window lookup runs before a server becomes active, and the fifo / lock descriptors (3, 5-9) are closed in the menu subshell, the cold terminal and the background spawn, so an app started from a menu action can never keep `menu.lock` / `server.lock`. The window switcher hides the `fzf-menu-server-a|b` terminals. `--size normal|large` (60% x 65% or 85% x 85% of the monitor; `keymap menu` uses large): `server_show` shows the window with ONE `hyprctl eval` chunk (`hl.dispatch(...)` statements: plain `toggle_special`, or `set_prop no_anim 1`, toggle, `resize`, `center`, `set_prop no_anim unset` only when size or monitor differ from the target). If a menu still shows motion on close, add `no_anim = true` to the two window rules (comment in `hyprland.lua`; menus then vanish instantly). Diagnostic for the owner: `infrastructure/tests/fzf-menu/watch-anim.py SECONDS` (read-only event + geometry log). **Hidden menu (FIX-MENU2)**: a menu counts as open and visible only while its window (`$RUN/active.win`, written with `active.pid`) is on a special workspace that a monitor shows (`hyprctl -j monitors` `.specialWorkspace.name`) or on the active workspace of a monitor (cold window); one `clients` + `monitors` call, only when the lock is held, so the hot path is unchanged. A second call over a HIDDEN menu (another window took the focus and Hyprland hid the special workspace) cancels it (fzf gets TERM, its caller status 1) and opens its own menu instead of being read as "close the open menu"; unknown (no address, unreadable answer) keeps the old close rule. While a server menu is open `watch_menu` (a background child of the menu subshell) reads the Hyprland event socket (`socat` on `.socket2.sock`: `activespecial`/`activewindow`/... wake a check, 5 s read timeout as safety net; 500 ms polling without socat) and cancels the menu when its window stays hidden for `FZF_MENU_HIDE_MS` (1000), never while the menu window itself has the focus; a shorter hide is kept. Tests: `infrastructure/tests/fzf-menu/run.sh [--quick]` (fake hyprctl, fake terminal in a private tmux; doctor `fzf-menu-tests`). An old live server keeps serving until it is restarted (hub > Fix > fzf-server), the protocol is compatible. `fzf-menu --self-test` drives the modal in a private tmux (doctor runs it). Every private tmux server of a test suite or tool (`tmux -L name`) removes its socket file after `kill-server` (which leaves it behind; `infrastructure/tests/tmux-sockets/run.sh` runs the suites with an empty `TMUX_TMPDIR` and checks, doctor `tmux-sockets` counts the dead ones). Image previews (clipboard, window switcher icons) use chafa through `.config/fzf/image-preview.sh`: fzf shows kitty graphics only as Unicode placeholders, so the script unwraps chafa's tmux-passthrough output (inside tmux it falls back to character cells). New menus: call `fzf-menu`, give NORMAL keys through `FZF_MENU_NORMAL_BINDS` and `--expect` Alt keys; never call `rofi -dmenu` (doctor checks).
