# Dev environments (mise, envs)

Topic file of the agent docs. `CLAUDE.md` holds the index, the rules that apply everywhere and the file of every section; section names quoted in the text ("Users", "Dev tools", ...) are listed there.

### Dev environments (DEV-b: mise + envs)
**mise replaces direnv** (the hook, the package and the dead nvm lines are gone). `.config/zsh/mise.zsh` (sourced from `.zshrc` after the last PATH change) returns at once when mise is missing; humans get `mise activate zsh` from a cached init file (`~/.cache/zsh/mise-activate.zsh`, regenerated when the binary or the script is newer), agent and non-tty shells (`$CLAUDECODE`, no tty) get **shims** only (a snapshot never runs precmd, so `activate` would freeze a stale PATH). `DF_MISE_MODE=activate|chpwd|shims` (never a `MISE_*` name: mise reads those as settings; set it in `~/.zshrc.local`) moves humans to the cd-only hook (`chpwd`: the per-prompt `_mise_hook*` is removed) or to shims when `hook-env` costs too much per prompt. **Install on cd** is automatic and trusted-only: a chpwd hook notices a new or changed mise config, asks `mise ls --current --missing` (an untrusted `mise.toml` makes that fail, so nothing is installed) and runs `mise install` detached; the next prompt prints one line (log in `$XDG_RUNTIME_DIR/mise-auto/`); `DF_MISE_AUTOINSTALL=0` turns it off. The legacy version files (`.tool-versions`, `.nvmrc`, `.node-version`, `.python-version`) need no `mise trust`, so a fresh clone with one must not start an install by itself (a registry tool backed by an asdf/vfox plugin is third-party code): for them the hook only prints a hint line; the global config also sets `disable_backends = ["asdf", "vfox"]` (key unverified until G7). The global `.config/mise/config.toml` has **no `[tools]`**: outside a project pacman go/node/python and rustup stay in charge (Claude Code, Mason, npm -g CLIs, nvim untouched); projects pin in `.mise.toml` (or `.nvmrc` / `.node-version` / `.python-version`, enabled as idiomatic files); `trusted_config_paths` stays empty and trust is its own question: `envs trust` (also offered right after `envs bind` and, on a terminal, `envs init`) lists the config files, says that mise can run commands from them with the environment's secrets and that trust is path-based (a later `git pull` that edits the file is trusted too), and only then runs `mise trust`; bind, init and the first `envs run` never imply it and never re-trust silently (without trust, `mise exec` refuses the config with its own message). Whether mise's `paranoid` mode (hash-based trust) fits is a G7 check. Inside a project a pinned old node/python shadows the system one for npm -g CLIs and Mason LSPs: `cd ~` or `mise exec node@system`. Managed users (td, yc) get their own mise installs (the cli profile links `.config/mise`); no `/srv/mise-shared`, because td's agents run `mise use` themselves. Both packages come from `apply-system.sh --only install` (`mise usage`; `direnv` is in the remove list). `sysup` has a `mise` step after `go` (`plugins update`, `upgrade --yes`, `prune --yes`; skipped without mise) and starts the install run with `cd $HOME` plus `clean_project_env`: a terminal inside an activated project would otherwise leak the project's PATH (mise install dirs, shims), `MISE_ENV`, `__MISE_*` and its `[env]` (`GOBIN`, `NPM_CONFIG_PREFIX`) into `go install`, `npm -g` and `mise upgrade`; the project environment is undone by mise itself, never decoded (`__MISE_DIFF` is base64 of zlib-compressed MessagePack `{v, old, new, path}`, values hashed since schema 2: read from upstream `mise-util/src/env_diff.rs`): when `__MISE_DIFF` or `__MISE_SESSION` is set, `mise hook-env -s bash --force` runs from `$HOME` (only `/usr/bin/mise`, never a PATH lookup, with `MISE_EXPERIMENTAL=0`, 30 s timeout; `HOME` is the account's from the password database, because a project's `[env]` can set `HOME` and the undo would then run inside the project; this whole undo comes BEFORE `sudo -v`, so nothing of a project runs with a fresh sudo timestamp; `SYSUP_TEST_HOME` is the test hook for HOME and counts only with a scratch `XDG_STATE_HOME`) and its output (the reversal of the old diff: `[env]` variables and `_.path` entries, plus whatever applies to `$HOME`) is `eval`ed; then the mise install dirs and shims, `MISE_ENV` and `__MISE_*` are removed. If mise is missing or fails, the run stops with exit 1 and says so (an activated project environment is never left in place); `SYSUP_KEEP_PROJECT_ENV=1` continues anyway. `SYSUP_MISE` is a test hook honoured only for a file below `<repo>/infrastructure/tests/` (`tests/sysup/fake-mise`). G7: check on the real mise (start sysup from an activated project with a `GOBIN` in `[env]` and look at `go env GOBIN` inside the run). `mise plugins update` pulls third-party plugin code that later runs inside `envs run` (with secrets): accepted.

**`envs`** (`.local/bin/envs`, absolute `#!/usr/bin/python3 -I`; public helpers in `.config/envs/`) keeps vault values out of the parent shell, command arguments and committed configuration. Project metadata in `.envs.toml` describes environments/protection/tool settings; secret names may instead be declared directly by exact references in the approved root `.env`:

```dotenv
DATABASE_URL=bw://Env/my-project/dev#DATABASE_URL
APP_PORT=8080
```

- **Automatic execution**: `envs bind` authorizes the exact source/target set once and pins item UUID/type/field metadata without fetching values. Then `envs run -- COMMAND` / `er COMMAND` resolves selected fields into the child environment, overriding stale same-name exports; `ere ENV COMMAND` selects an environment. No duplicate `[secrets]` declarations are needed. A reference-only project can omit `.envs.toml`; human binding stores its project identity locally. `envs agent allow -- EXACT_COMMAND` can create minimal project policy metadata after confirmation. `ENVS_SECRETS` contains injected names only. Bare binaries do not understand `bw://`; they must enter through this runner. Plain lines remain ordinary application configuration.
- **Exact references**: `bw://FOLDER/SUBFOLDER/ITEM#NAME` selects a custom field; `#field:ENCODED_NAME` supports other field names and distinguishes a custom `password` from built-in `#@password`. Built-ins are `@password`, `@username`, `@notes`, `@uris`; TOTP/history/SSH private selectors are excluded. Folder case is significant; names use UTF-8 percent encoding and NFC, with no URL-host interpretation, network access, globbing, expansion or recursive reference resolution. Item names containing slash are unsupported. Owner-only `bw://@root/ITEM#@password` addresses an exact unfiled item. Managed accounts use only concrete targets already permitted by their root-owned broker scopes; a reference grants no new access or fallback. Legacy `[secrets]` remains supported; only an exactly equivalent owner or managed-self target coalesces with a reference. A concrete managed target does not silently become own-plus-Shared fallback.
- **Sources and approvals**: discovery uses the nearest metadata root, its git root with `.env`, or the current directory; it never climbs arbitrary home directories. Default source is root `.env`; human `envs bind -e ENV --ref-file RELATIVE_PATH` (repeatable) selects alternatives. New `.env.local` files are not adopted automatically. No-follow, bounded, owner-owned, regular/single-link source checks reject credential locations. Duplicate secret/reference assignments fail at runtime. Changed source identity, mapping, selector, root or item identity requires human reapproval; same-item field rotation works automatically. Protected environment names and known Env/prod targets remain unavailable to agents, including `--prod`; `bind --protect-ref NAME` adds durable local protection for arbitrary targets.
- **Metadata commands**: `status [--json]`, `check`, `refs list` show names/source/approval state without vault access; human `--vault` explicitly opts into the older vault inspection. `refs list --locations` also prints exact private locations. `envs refs set --file .env NAME 'bw://...#NAME'` validates and updates only reference metadata, preserving unrelated spans and invalidating authority while retaining protected classifications. This narrow operation is available under agents, makes no vault call and refuses to replace a literal credential; the human runs import instead.
- **Import**: `envs import [FILE]` classifies every literal assignment as secret/plain/drop, refusing the entire document on unsupported syntax. Explicit complete `--secrets A,B --plain C --drop D` classification is available without a terminal; drop needs confirmation or explicit human `--yes`. Secret writes use the existing exact project/environment hidden fields; all conflicts are checked first, remote writes/readback/refresh succeed before local redaction. Every duplicate secret span becomes one canonical reference; plain bytes/comments/line endings stay intact. Default import keeps `.env`, adds no redundant TOML names and never shreds it. `--plain-to-mise` explicitly copies plain selections into mise; `--keep` leaves the original plaintext entirely unchanged with a warning. Conflicting existing fields require `--overwrite`; identical values make retries idempotent. Tracked files change only in the working tree, never staged. Old history, retained recovery copies and already-running shells may still contain credentials; rotation is an owner decision.
- **Locked vault for managed users**: td and yc read the OWNER's vault through the broker; an rbw agent of their own is never consulted (and is not part of the design). Their envs therefore says `the owner's vault is locked (this account reads it through the vault-share broker; its own rbw does not count)` while the owner's rbw-agent is stopped or locked, even when `rbw unlocked` in the managed account prints 0; the fix is an unlock in the owner's session. The broker journal (`journalctl --user -u vault-share`) shows `result=locked` with the peer uid.
- **Native managed writes**: td alone has the root-rendered `env-write` capability; yc and service accounts remain read-only. In td's own project, `envs bind`, `envs import .env`, `envs bind`, then `envs run -- go run .` works with inline references and no required `envs init`/TOML. Import keeps plain bytes and writes `bw://Users/td/Env/PROJECT/dev#NAME`; `envs set NAME --stdin` or its hidden prompt creates/updates that exact own inline field, never a Shared/cross-user/custom-selector target. Global import maps only that account's `global.env`. Existing optional TOML declarations may coexist only with equivalent self references. Native set supports one environment and inline secrets; other mutation families and Send remain owner-only. Limits: 64 fields per batch, 100 ASCII characters per name, 6–5000 characters/20,000 UTF-8 bytes per value, and 256 KiB per request; larger batches refuse whole rather than splitting writes. The broker derives scope from the peer UID and a fresh root policy, writes only its own machine-marked personal Secure Notes, preserves unrelated fields and verifies exact fresh readback plus prompt-free rbw visibility. Existing unmarked/protected/organization notes are refused, with no automatic adoption. The client independently verifies scoped selected-field readback before local redaction, retains private recovery and a metadata-only request UUID after uncertainty, and never automatically retries a mutation. Ordinary retry reconciles the original request without replaying a mutation; changed unresolved work is refused. Human-only `envs import --resume-pending` is a separate renewed authorization for that same stored UUID and HMAC-bound target/values/overwrite payload. It requires a real terminal and typing `resume`, even with `--yes`; no new UUID, journal deletion or automatic legacy replay occurs. The broker may continue an absent-note legacy/pre-item request only after fresh checks; item-dispatch uncertainty still blocks recreation. Existing matching notes reconcile without another write. Current source stability is checked throughout this attempt; old records do not prove a historical source inode or that no write was previously dispatched. Fixed error category/stage diagnostics survive to the CLI, while unknown or poisoned backend text is discarded. The broker retains a metadata-only, keyed request journal under `~/.local/state/vault-share/env-write` (0700; files 0600); it keeps spent request IDs and fails closed at 4096 spent IDs or 8192 records instead of evicting unresolved work. Owner session/server setup remains a prerequisite. Apply the reviewed policy with `sudo ./apply-system.sh --only users`, then restart the owner's active broker with `systemctl --user restart vault-share.service`; absence/revocation of `/etc/vault-share/env-write.tsv` restores read-only behavior. With policy already installed, a code-only repair needs `usr sync` and the owner broker restart, without another root-policy apply. No concurrent external editing of the same self-managed note during a write: server APIs provide no atomic conditional update. This capability belongs to the td UID, including same-UID processes; CLI agent refusals are defence in depth, not broker authentication.
- **Go shortcuts**: interactive `grun` retains its main.go/cmd/main.go/cmd/api/main.go selection and `tg` forwards arguments to `go test ./...`. Configured projects use readonly `_ENVS_BIN run -- go ...`, preserving binding/approval/masking and failing without a raw-Go fallback. Truly unconfigured projects run Go directly; a plain-only `.env` still counts as configured and retains the normal envs binding requirement. These functions do not export secrets into the parent shell and do not change ripgrep.

Project-local agent instructions may use this explicit command contract (no global instruction file is installed):

```text
This project stores secret references as bw:// entries. Run secret-dependent commands
through envs run -- COMMAND (for example, envs run -- go test ./...).
Do not retrieve, print, expand or copy literal vault values, or replace bw:// entries.
If envs reports missing human approval, a locked vault or a policy error, stop and ask
for that setup; do not retry the command outside envs. Shell aliases are optional.
```

- **Private recovery**: original imports are backed up as 0600 files in 0700 `~/.local/state/usr/secrets-backups/envs-import-*`; transaction records contain names/phases only. Source replacement uses Linux atomic exchange, checks the displaced inode/content and current parent, and conditionally restores ordinary concurrent edits. Ambiguous displaced versions are retained privately, including across filesystems. Absent destination publication validates the pinned parent/inode/payload, and all destinations are rechecked before retiring an external source. This is not a multi-file or malicious same-uid compare-and-swap transaction; failures require review/retry with preserved sources/backups. Ambiguous source recovery under protected `~/.local/state/envs/recovery` can contain original plaintext and is never a metadata log.
- **Global import and wrappers**: human `envs import -g ~/.config/secrets/env.sh` strictly parses literal shell assignments without source/eval; secret fields go to `Env/global/default`, their refs to private user-owned `~/.config/envs/global.env`, and deliberate plain exports remain in canonical `secrets/env.sh`. Neither global.env nor `global.local.toml`/`wrap.tsv` is stowed or published. Existing declarations in global.toml/global.local.toml remain valid. Scoped `--for USER`/`--shared` global import writes only vault fields and retains the source; it reports target mapping still pending and saves exact metadata privately in `~/.local/state/envs/scoped-global-import.json`. It never writes the owner's global map or routes plain exports to the wrong account. The target user can authorize `envs refs set -g NAME 'EXACT_REFERENCE'` followed by `envs bind -g`; source retirement waits until the operator verifies that setup. `envs global-wrap NAME /absolute/COMMAND --only A,B`, `--list`, `--remove NAME` manage private 0600 TSV metadata. `usr link` prepares only the real user-owned `.config/envs` directory as 0700 without access/default ACLs before linking public modules, preserving local files and publisher ACLs on home/`.config`; dry-run validates without writes and unsafe owners/symlinks refuse. `.config/zsh/envs-wrap.zsh` validates the whole file before installing literal `functions[]`, loads once with no Python/vault query and uses readonly passwd-home `_ENVS_BIN`. Only home and `.config` may retain effective named-user writers limited to the user, root and the publisher from the checked root-owned `/etc/usr-managed/devtools-owner`; owning/named group writers and other writers refuse. The envs directory and wrapper file retain strict private checks. It supplies the backward-compatible `/usr/bin/glab` default; a validated local row may replace it. Wrappers grant no agent approval.
- **Approved agents**: `[agents] allow = ["go test ./..."]` uses exact shlex argv-prefix words, never shell/glob matching. Human-only `agent allow [-e ENV] -- COMMAND` shows prefix/binding/environment/effective names, confirms, records a missing exact policy rule and pins local approval/executable resolution; the vault metadata is read before the confirmation, so a locked vault leaves no half-written `[agents]` rule. Human-only `agent allow [-e ENV] --any` is one approval for every command of that project/environment: it lives only in the private `agent-approvals.json` (no `.envs.toml` or other project file is written, nothing reaches git), pins no executable, and still refuses the forbidden families, protected targets and changed mapping/sources/policy (the row digest includes the project `[agents] allow` rules, so clean a stray rule before approving); `agent deny --any` revokes it. `agent deny` revokes even stale policy, `agent list` shows prefixes and `--any`. Project changes cannot self-authorize; global policy lives only in private global.local.toml and has separate approval. Protected/global checks, changed policy/targets/executable, forbidden command families and `--allow-missing`/`--sync` refuse before fetching values or starting a child. Only the selected `--only` fields are fetched. Shells, environment printers, escalation/detachment/multicall/generic wrappers and interpreter eval/stdin entrypoints are refused by requested and resolved names. Explicit trusted script/task code still runs by design. The outermost mise/tool stdout and stderr are independently masked as bytes: raw values, standard/URL base64 with/without padding, URL/form percent escapes and hex. Identical values use sorted combined labels; overlapping coverage and every chunk split are bounded, nonsecret output streams immediately, queues are bounded, and no raw fallback exists. Required one-decision audit uses logger stdin with project/env/command basename/names/result, never argv/values. Audit failure prevents launch.
- **File-preferring consumers**: `envs run --env-file [--env-source APPROVED_RELATIVE_FILE] -- COMMAND '{envfile}'` renders only selected fields and omits unselected reference assignments. The exact placeholder is substituted as argv data, never shell code. The supervisor keeps a verified 0700 tmpfs run directory/0600 file under `/run/user/UID/envs` or private `/dev/shm/envs-run-UID`; no persistent/project fallback. It forwards INT/TERM/HUP, restores human terminal foreground ownership, reaps/terminates descendants and cleans on success/error/signals. SIGKILL/power failure cannot clean immediately; only positively dead/reused, validated own runs are cleaned later, and tmpfs disappears at reboot. Child daemonization is unsupported. Generic file serialization is a deliberately limited literal subset: actual LF/tab and a quote type absent from the value; `$`, backslash, CR/control bytes or both quote types refuse before child launch. Exact subset roundtrips and process precedence are verified offline with python-dotenv 1.2.4, dotenv 17.4.2, Compose 5.6.0 and Vite 6.4.3; godotenv Load/Overload remains unverified/SKIP. Override APIs differ; Compose interpolation differs from service env_file. No universal dotenv precedence/escaping claim. Public-prefixed Vite values can enter client bundles.
- **Human Send**: `envs send [FILE] [-e ENV] [--prod] [--only A,B]` renders an approved source into an owner-only Bitwarden text Send, fixed one access/one-day deletion, default maximum 512 UTF-8 bytes. Explicit `--file-send` permits up to 4 MiB and is a file Send with one-download semantics and verified tmpfs cleanup; unsupported entitlement/size never silently falls back. Send uses the separate lossless **envs literal transfer dialect**, preserving dollar/backslash/quotes/newlines; read/import it with envs, never source it as shell or assume every dotenv library decodes it identically. The link is copied sensitive through trusted absolute clipboard tools, never printed/logged/notified; only the original copier is expired, without clearing a replacement selection. Metadata-only pending-ID recovery prevents duplicate creation after uncertain remote/copy failures; `envs send --recover UUID` retrieves/copies that existing Send. Example: `cd PROJECT && envs send .env`; use `envs send .env --file-send` only explicitly. Neither original source nor vault fields are rewritten by sending. Recipient access is a service-side count, not a guarantee against saving received content.
- **Inventory**: human-only `envs scan [DIR] [--json] [--depth N]` reports names and secret/plain/unknown/reference guesses, templates and safe parse-error locations only. It prunes build/dependency/credential/coordination locations, rejects symlink/hardlink/device/FIFO/oversize files and linked/mounted escapes, calls no backend and modifies nothing. A guess never authorizes import.
- **Threat model**: approvals and finite masking reduce accidental transcript leaks; approved code can send secrets through network/files/another fd/tty/children or transformations the matcher does not recognize. Cross-stream splits, ANSI-separated/composite encodings and arbitrary transformations are not universal DLP. Same-uid processes can inspect environments/state or use an unlocked owner vault/scoped broker directly; detached/reparented ancestry and tty checks are not authentication. Owner access remains full-vault, managed access remains broker-scoped, and docker-group root equivalence remains until ROOTLESS. This is no sandbox, malicious-agent isolation or core-dump confidentiality guarantee. Review changed workflows/code before approving tasks. Value-revealing and mutation commands remain refused under recognized agent ancestry; refs set is the narrow metadata exception.
- **Tests and doctor**: `infrastructure/tests/envs/run.sh [--quick] [--only=N]` keeps the existing fake-vault/broker regressions and adds literal/ref/import/policy/wrapper/runtime/metadata cases. Full mode runs actual offline loader probes (no installs/network/daemon), stream/signal/lifecycle integration and timing; unavailable libraries print SKIP. Doctor validates source/approval file metadata and shell/profile wiring, never reads dotenv/shell-export payloads or fetches vault values; full semantic policy/executable checks run again before every approved command. Names-only dev launchers consume the effective ref/declaration union. No agent ran a real import, Send, vault request or clipboard operation during implementation.
