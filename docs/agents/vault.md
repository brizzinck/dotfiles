# Passwords and 2FA (rbw, bw, vault browser, Linux passwords)

Topic file of the agent docs. `CLAUDE.md` holds the index, the rules that apply everywhere and the file of every section; section names quoted in the text ("Users", "Dev tools", ...) are listed there.

### Passwords and 2FA (from "Hubs and window tools")
- Passwords and 2FA: Bitwarden/Vaultwarden through `rbw` + fzf-menu (`SUPER+CTRL+P` passwords: `rbw list` picker, Enter types user+Tab+password with `wtype -` from stdin, `SUPER+CTRL+O` 2FA codes, waybar `custom/vault`, hub rows in `actions.d/u5.tsv`; logic in `scripts/vault.sh` + `vault-totp.py`). One-time `bw-setup` (asks server URL and e-mail; they live in `~/.config/rbw`, never in the repo); Hyprland runs `vault.sh session-start` (`rbw stop-agent`) at login so the master password is asked once per session. `2fa-import` converts a Google Authenticator export QR into a Bitwarden CSV on tmpfs and offers `Import now with bw? [Y/n]` (`vault-bw.py import-csv`: pinentry unlock, `bw import bitwardencsv`, `bw sync` + `rbw sync`, then `shred -u`; the web-vault steps stay as the fallback). User commands live in `.local/bin/` (stowed per file). Copied secrets use `wl-copy --sensitive` (cliphist skips them) and are cleared after 30 s. Full Bitwarden (U6): the desktop app (`bitwarden`, Wayland via `.config/electron39-flags.conf`, floating window rule, waybar middle click) and the official CLI `bw` with hub rows in `actions.d/u6.tsv` (new login, generator, Send text/file, attachments, history, edit, delete; logic in `scripts/vault-bw.py`, session key only in `$XDG_RUNTIME_DIR/vault/bw-session` (every `bw` process that holds it runs non-dumpable through an `LD_PRELOAD` library with `prctl(PR_SET_DUMPABLE, 0)`: built per boot into `$XDG_RUNTIME_DIR/vault/nodump-<hash>.so` under a file lock, probed once, a marker holds its sha256 so a corrupt file is rebuilt; a failed build is retried by the long-lived server after `VAULT_BW_NODUMP_RETRY` seconds (120), not kept for the whole session; `vault-bw.py nodump-status` is READ-ONLY (library present with a matching marker; it compiles nothing, so doctor has no side effects) and `nodump-build` builds and probes, doctor `vault-nodump` also checks that the running `bw` processes have a root-owned `/proc/PID/environ` (INFO when the library cannot be built or a process predates it); `bw-setup`'s first sync goes through `vault-bw.py sync` for the same reason), cleared with the rbw agent at login and by lock; the master password reaches `bw unlock` only through a pipe (`--passwordfile /dev/fd/N`), never argv or environment; every bw process that holds `BW_SESSION` is non-dumpable (`PR_SET_DUMPABLE 0` through a tiny `LD_PRELOAD` library that `vault-bw.py` builds with `cc` into `~/.cache/vault`, `VAULT_BW_NODUMP=0` disables it): `RLIMIT_CORE=0` alone only stops the core file, systemd-coredump still journals the whole `COREDUMP_ENVIRON` (verified here), readable by the `wheel` group of td/yc; `bw-setup` also logs `bw` in). Opt-in SSH keys from the vault: `vault.sh ssh-agent on` (flag in `~/.local/state/vault/`) makes shells use the app's `~/.bitwarden-ssh-agent.sock` only while it exists; import a key in the app (New > SSH key), verify with `SSH_AUTH_SOCK=~/.bitwarden-ssh-agent.sock ssh-add -L`. `oo7` is in the package list to satisfy the `bitwarden` package's `org.freedesktop.secrets` dependency; the greetd PAM service runs `pam_oo7` (auth + session `auto_start`), so the oo7 "Login" collection is unlocked (created on the first login) with the login password (only when `oo7-daemon.service` already runs at that moment: `install.sh` enables it in the user manager, which linger starts at boot; a daemon that pam_oo7 has to start itself fails to receive the secret, seen in the journal as `Failed to send secret to oo7 daemon`; doctor `oo7-daemon`); without it the desktop app waits at its start for a Secret Service prompt that never comes (endless spinner). Vault browser (U9): `SUPER+CTRL+SHIFT+P` (`vault.sh browse`, hub row + leader `v b`, `.local/bin/vault-browse [--here] [FOLDER]`, logic in `scripts/vault-browse.py`) is our own fzf-menu list of every item (login, card, identity, secure note, SSH key; there is no maintained Bitwarden TUI). Tab / Shift+Tab cycle the folders (All, each folder, no folder, Trash; shown in the header; the state is a per-run file read by the fzf `transform-header` + `reload-sync` binds, which call `vault-browse.py header --cycle` and `rows`); the preview shows every field with secrets masked (card number last 4, notes as a line count), the live TOTP code with seconds left (ticked through `--listen`), custom fields (hidden ones masked), URIs and attachments. Keys are NORMAL letters (the library twins them) plus Alt keys in both modes (`NORMAL_KEYS` / `ALT_KEYS` at the top of the file, listed in `.config/keymap/static.tsv`): y copy password (card number, SSH private key, note text), u user, o TOTP, f any field (picker), t type user+Tab+password (P / Alt+P password only; Enter does `t` for logins and opens the field picker for other types), e edit, n new, d trash (permanent in the Trash, confirmed), r restore, h history, F (Alt+A) attachments, w generator, S (Alt+M) Send, s sync, L lock, b unlock bw, O (Alt+V) app; the last list row (Enter) opens the desktop app for account settings, emergency access and organisations. rbw does the list, previews, copy, type, TOTP, history, sync and lock (it exposes every item type incl. SSH keys); bw (through `vault-bw.py`, imported, session key as before) does what rbw cannot: Trash, attachments, edit, new, delete, restore, Send. The bw side needs the CLI session; it is opened on demand (Trash row / `b` / any bw action: pinentry once per login). **Backend (BW1)**: `bw` itself is a ~0.93 s start per call (a pkg-compiled binary, rbw is ~3 ms), so rbw does every read it can (lists, the pickers of delete / attach-to, `get`, TOTP, history, sync) and everything only bw can do goes through ONE per-session `bw serve --hostname unix://$XDG_RUNTIME_DIR/vault/bw.sock` (verified with bw 2026.10.0: the `unix://` prefix is the form, not `unix:`; the Host header must be `localhost:8087`, which is never bound; no TCP listener ever, doctor `vault-bw-serve` fails on one). `vault-bw.py` is the one client: `bw()` translates the CLI arguments into REST (`http.client` over an AF_UNIX connection: status, sync, list items/folders incl. `--trash --folderid --search`, get item/template/attachment, create item/folder/attachment, edit, delete `--permanent`, restore) and returns the same `CompletedProcess` the CLI would, so every call site is unchanged; what has no REST form (Send, import, passphrases) or when the server cannot run it falls back to the CLI process (`VAULT_BW_SERVE=0` forces that). Plain character passwords are generated locally with `secrets` (no `bw generate`); `vault-bw.py call [--stdin] BW-ARGS...` is the entry for shell scripts (`linux-pass`), so no `bw` call is left outside `vault-bw.py` except `bw-setup`'s login. The server is the supervisor `vault-bw.py _serve` (a transient user unit `vault-bw-serve` via `systemd-run --user`, so it outlives the float.tui window it was started from; a detached child without a user manager): it reads the 600 session file, puts the key into the environment of the one `bw serve` child (never argv, never a unit property; the child dies with the supervisor, PDEATHSIG), the socket is chmod 600 in the 700 `vault` directory (the runtime directory's default ACL for td / tgconfirm ends as mask `---` there; doctor runs `acl-reach.py` for the other users), log 600 without secrets. It starts when a bw action needs it and a session key exists (flock against double starts; unlock starts it with the new key and syncs through it), and stops on `vault.sh lock` / `L` (SIGTERM to the supervisor, then one `bw lock` process: the real `bw serve` exits by itself on `POST /lock`, so that is not relied on), on `session-start` at login (linger keeps the user manager, so a server of the previous login would survive), when the rbw agent locks after having been seen unlocked, and after 15 minutes without a request (`VAULT_BW_IDLE` seconds; the rbw `lock_timeout` when that is shorter, it is a year here, so the cap is what applies); the rbw lock is looked for every 20 s (`VAULT_BW_RBW_POLL`, one `rbw unlocked` process each, not every 2 s); an idle or rbw stop keeps the session key, the next bw action starts it again (about 1 s once). Hardening (BW1-fix): the client trusts the socket only inside a real, 700, own-user `$XDG_RUNTIME_DIR/vault` (`RUN` has no `/tmp` fallback, it is `/run/user/UID`; a symlink, foreign owner or group/other bits mean the CLI path) and only after `SO_PEERCRED` says the peer is this uid, before a byte is sent; the supervisor, its bw child, popen launches and every bw CLI process run with `RLIMIT_CORE` 0 and the transient unit has `LimitCORE=0` (no core file with `BW_SESSION`); `lock` reads the key, removes `bw-session` first, stops the server under the same flock `start_serve` holds, then runs `bw lock` with the key it kept in memory (a client cannot restart the server with the key being locked); attachments go out with `filename*=UTF-8''...` plus an ASCII plain `filename` (quote/CR/LF percent-escaped), because busboy behind `bw serve` reads a plain name as latin1; `start_serve` stops a slow first server before launching the next. `linux-pass` reads the folder through `load_items` (rbw, then bw) and never treats an unreadable folder as an empty one, so a locked rbw cannot create duplicate items. Managed users td / yc have no rbw or bw of their own (BW-ORG): they reach their part of the vault through the vault-share broker (see "Vault reorganisation" below). Typing keeps the type-guard rules (target recorded before the first menu, `tg_ok` before every `wtype -`, text on stdin). Edit = `bw get item` JSON plus a `_folder` helper key (folder by name, created when new) in a 600 file under `$XDG_RUNTIME_DIR/vault/edit/`, edited in `$VISUAL`/`$EDITOR` (nvim with no swap/undo/backup/shada), validated (JSON, same id and type, non-empty name; invalid = edit again or discard), sent to `bw edit item` on stdin and shredded; new card/identity/note/SSH key use `bw get template` the same way (SSH key falls back to a built-in template), a new login reuses `vault-bw.py new-login` in the open folder. Steps that read the keyboard (editor, prompts) run in this terminal or, from the float.tui menu, in a float.tui ghostty of their own (`_act`, `VAULT_TERMINAL` test hook). The only cache is `$XDG_RUNTIME_DIR/vault/browse-index.json` (names, folders, attachments, masked fields, never a value; 600; exists only while bw is open, dropped on lock/sync/change/login). Test: `infrastructure/tests/vault-browse/run.sh` (fake rbw/bw/wl-copy/wtype/pinentry/editor and a fake `bw serve` with the real server's REST shapes, private tmux, checks that no secret reaches argv, `ps`, the screen or a notification; BW1 cases: server vs CLI fallback, socket 600 / dir 700 / no TCP, key only in the child's environment, lock / session-start / idle / rbw-lock stop, stale socket after a kill -9, unit launch, `linux-pass`; `--quick` skips tmux and the slow cases and runs in doctor, `ONLY=2,5` picks sections, 14 = idle / rbw lock / unit). `measure.sh --old DIR` prints before / after bw process counts and seconds per flow with a fake bw that sleeps 0.9 s per process. Linux passwords (U8, `SUPER+CTRL+U`, `vault.sh user-pass`, hub row `vault-user-pass`, leader `v u`): types the password of the Linux user the focused window's prompt is for, without Enter (`wtype -` from stdin). Storage: Bitwarden folder **`Linux`**, one login per Linux user, item name = the user name exactly (`skalse`, `td`, `root`, ...), Username = name, Password = password (the owner creates them; doctor `vault-linux` is INFO only). The user comes from `scripts/vault-who.py` (read-only, prints JSON; `vault.sh user-pass --dry-run` shows the decision without a password): a terminal window (class list or the window process is a known terminal; `float.tui` menu terminals are excluded) -> the foreground process group of its pty; a tmux client there -> its session -> the active pane -> that pane's foreground group (a tmux server of another user, the `tdterm` window, cannot be queried, so its panes are read from /proc: one pane or all agreeing, else the panes waiting at sudo/su/doas, else undetermined). Prompt rules: `sudo`/`doas` -> the invoking (real) uid, never root (a sudo that already runs a command is followed into the command); `su [-] NAME` -> NAME, plain `su` -> root; `ssh`/`passwd`/shell/other -> the real uid of the foreground process; the `hyprpolkitagent` dialog -> the session owner (its identity is not visible outside the agent). Unknown user or no item for it -> an `fzf-menu` picker over the folder. `linux-pass` (U8b, `.local/bin/linux-pass`, hub row `linux-pass`, leader `v k`; also for a fresh install after `bw-setup`) fills that folder: reads through rbw (`--list` and a setup with nothing missing never open bw), `bw` login check (offers `bw-setup`) and unlock through `vault-bw.py` only when something is written (pinentry; a master-password prompt on the terminal without a display; locks `bw` again only if it unlocked it), then for `root` and every uid 1000-59999 user with a login shell it skips existing items and asks for the missing passwords on the terminal (no echo, twice, Enter = skip); `--update NAME` replaces one after `passwd`, `--list` shows names and local users without an item; the password only goes to the environment of the one `jq` that builds the item JSON (then `base64 | vault-bw.py call --stdin create item`), never argv. Safety: text goes only into a terminal or the polkit agent and only while that window is still focused (`type-guard.sh`; pinentry is never a target); any other window gets `wl-copy --sensitive` (cleared after 30 s) plus a warning notification. The bind waits in Lua (`exec_when_keys_up`, `hl.is_key_down` + `hl.timer`) until SUPER and CTRL are released, because Hyprland combines the modifiers of all keyboards and wtype would otherwise fire binds. If rbw is locked it unlocks through pinentry and the script puts the focus back on the window the key was pressed over.
