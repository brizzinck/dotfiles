# Vault reorganisation and sharing (vault-audit, vault-share)

Topic file of the agent docs. `CLAUDE.md` holds the index, the rules that apply everywhere and the file of every section; section names quoted in the text ("Users", "Dev tools", ...) are listed there.

### Vault reorganisation (from "Hubs and window tools")
- Vault reorganisation (BW-ORG): `vault-audit` (`.local/bin/vault-audit`, logic in `scripts/vault-org.py`, stdlib, values compared only in memory) tidies the one Bitwarden account into a folder tree: `Shared/**`, `Users/<u>/**`, the owner's own tree, and the tool folders `Env/<project>`, `Linux`, `MCP` with their names unchanged. Every name, host and value in its tests is invented. **Audit** (`vault-audit [audit] [--names-hidden] [--json]`): three requests through the bw server (items, trash, folders; a closed bw session asks the master password through pinentry, but under an agent ancestor it is exit 3 and the owner runs it himself) -> `$XDG_RUNTIME_DIR/vault/org/audit.json` (600, tmpfs, removed by `vault.sh` lock/login like the browse index; ids, names, hosts, flags and counts only) and a report: items without a folder, duplicate groups (same type + host set, or name when there is no host, + username; class `identical`, `same-login` with `differs` = password / totp / notes / complete custom fields / password history / full URIs and match settings / exact username / every type-specific field / policy, `no-user` = logins without a username next to one with; `keep` = the member with the most data, ties the newest revision; every member has a relation to the keep: `identical`, `subset`, `differs:KIND` or `review:REASON`), near-duplicate folders and names, empty folders, tool-folder problems (a `Linux` item that is not a login or not a local user, an `Env/*` item that is not a secure note or a second item of one name), items carrying the `vault-share` custom field. Comparison v1 includes all supported credential fields and exact usernames; unknown item/type/custom-field/URI/history shapes, passkeys and attachments require review and can never be duplicate-trashed, even with a `manual` marker (attachment filename/size does not prove equal content). Secrets and usernames are only compared as HMAC-SHA256 under a random key that lives in that one process (so the audit file holds no hash); tool folders are never grouped, proposed or counted as empty. Exit codes 0 / 1 error / 2 usage / 3 locked under an agent / 4 refused / 5 apply finished with skips. Test: `infrastructure/tests/vault-org/run.sh [--quick]` (doctor `vault-org-test`). **Scopes** (`scripts/vault-share.py`, scope part): a rule is `user<TAB>P/**` (folder P and below) or `user<TAB>P/NAME` (one item, split at the last `/`), exact and case-sensitive after NFC; an item without a folder is never in scope; refused: `**`, `/**`, empty or `.`/`..` segments, control characters, any other `*`, a leading/trailing `/`, over 512 characters, user root / the owner / a non-login name (`vault-share.py check-scopes FILE`). The repo file `infrastructure/vault-share/scopes.tsv` has only generic rows (`*  Shared/**`, `*  Users/{user}/**`); the company rows live in the owner's `~/.config/vault-share/scopes.local.tsv` (0600, not in the repo; `install.sh` creates `~/.config/vault-org` and `~/.config/vault-share` 0700); `vault-share.py render-scopes` merges both for the interactive managed users (an overlay that is a symlink, not the owner's or group/other-writable is ignored with a warning). `Linux/<user>` is in NO scope: the Linux passwords stay the owner's (SUPER+CTRL+U types them from his session). **Plan** (`vault-audit plan [--rules FILE] [--force]`, default rules `~/.config/vault-org/rules.tsv`, format in `infrastructure/vault-org/rules.example.tsv`: `host|name|folder|type<TAB>pattern<TAB>folder`, first match wins, invented hosts only): `~/.local/state/vault/org-plan.tsv` (600, atomic; `id name current target revision note`, folder rows `@folder id name target - note`; targets `keep`, `folder:NAME`, `trash-duplicate-of:ID`; folders `rename:NEW`, `delete-if-empty`) plus `org-plan.meta.json` (sha of what was generated, reviewed ids, the proposals for reset). Proposals: tool-folder items stay; members that are `identical` or a `subset` of the keep go to the trash as duplicates, `same-login`/`no-user` members stay with a note; the rest follows the first rule; the items of the smaller of two near-duplicate folders move to the larger one and the empty one is deleted; a plan with manual edits or reviewed rows is not overwritten without `--force` (old one kept as `.bak`). `vault-audit check [--allow-tool-folders]` validates it (the same checks apply runs first): unique ids, target grammar, folder names without `*`, a duplicate target must exist, must not itself be trashed (no chains or cycles) and must be in the same audit group unless the note says `manual`, nothing moves out of or into a tool folder (`Linux`, `MCP`, `Env/*`, `Users/*/Env`, `Shared/Env`), tool folders are never renamed, deleted or trashed from, a rename onto an existing folder is refused. **Reviewer** (`vault-audit review`, hub row `vault-audit`, leader `v r`): an fzf-menu loop like the envs TUI (`--here`, NORMAL letters through `FZF_MENU_NORMAL_BINDS`, Alt keys through `--expect`, cursor restored with `load:pos`); rows `·`/`→`/`✗` keep/move/trash + `!` note / `✓` reviewed, folder, target and the `[td yc]` column computed with `in_scope` from `/etc/vault-share/scopes.tsv` (before the root layer exists: what apply-system would render, `(planned scopes)`); keys f folder picker (New folder... prompts, validated), n keep, d duplicate-of picker (outside the audit group it is marked `manual`), D trash the group, u undo, r reset, t filter all/changes/notes/duplicates/folders, e edit the whole plan in `$EDITOR` (validated), s summary, R rename a folder, Enter reviewed; every change is written at once. Test hooks `VAULT_ORG_CONF` (dir with `vault-org/` and `vault-share/`), `VAULT_ORG_SCOPES`, `VAULT_ORG_USERS`. **Apply** (`vault-audit apply [--dry-run] [--resume] [--new-journal]`): `--dry-run` is offline (plan + last audit, no vault, nothing written; allowed for an agent); a real run is refused under an agent ancestor (exit 4), needs the validated plan, `flock $XDG_RUNTIME_DIR/vault/org/apply.lock`, a `[y/N]` with the summary (no terminal = exit 4; `--yes` only in verified test mode) and a bw session (pinentry once). Order, each step one journal line `time<TAB>step<TAB>id<TAB>result` in `~/.local/state/vault/org-journal.tsv` (600, header `# plan-sha256=...`): `bw sync`; **verified encrypted backup bundle first**, fresh on every apply/resume: CLI-only sync/inventory and account-bound encrypted exports for personal plus every visible organization partition, exact unique item/folder IDs with revision/type checks, followed by another CLI snapshot and matching served metadata before mutation. Files are precreated O_EXCL/no-follow0600 in a private0700 pending directory, fsynced and certified by a metadata-only manifest before completion rename. Export permissions/partial/plaintext/incoherent results fail before mutation; organization extras are allowed only within that same partition. All completed and legacy bundles are conservatively retained, with no automatic pruning; an old journal backup row cannot bypass a fresh gate. Folder names stay in memory/encrypted personal artifact only. `vault-audit apply --backup-only` creates, verifies and retains the encrypted bundle under the same plan, agent, lock and authentication gates without confirmation or plan/journal/vault mutations; failed backup requests report only fixed stage/rc/category diagnostics, never backend output. The explicit one-time `vault-audit apply --personal-only` path accepts only item folder moves and keep rows, classifies personal versus organization ownership from fresh CLI metadata (official null/omitted ownership fields are equivalent), and shows one confirmation with effective personal moves, already-at-target/new-folder counts and scope projections while organization proposals stay unchanged. It preserves the original plan, metadata, audit and full journal; its exact personal encrypted backup covers every personal item and account folder, makes no organization export, and verifies the full metadata snapshot against the CLI and served backend. A separate `org-personal-journal.tsv` binds scope, original plan SHA and selected IDs/approved targets for `--personal-only --resume`; every resume needs a fresh scoped backup, and the manifest explicitly declares personal coverage. Only destination-folder creation and personal moves run; final GET checks exact identity, personal ownership, backed type/revision/source folder before PUT, and checks receipt identity/ownership/target, with fixed errors and a nonzero result on skips. `--personal-only --backup-only` verifies only the scoped bundle without confirmation/journal/mutation; its dry-run stays offline and cannot guess eligibility counts. The API has no conditional write, so a transfer between final GET and PUT remains possible: do not edit or transfer items concurrently. This is not a full attachments/history/restore guarantee: account-key exports require the original account/key, key rotation can invalidate them, organization restore needs authority, and imports do not de-duplicate; folder renames (`PUT /object/folder/ID`, parents created first); folder creates (every `folder:` target and each parent, looked up by exact name first); moves (GET the item, set `folderId`, PUT the fetched JSON, check `folderId` in the answer; an item in the trash is skipped); every mutation resolves fresh folder IDs/names and refuses live protected source or target folders, missing/ambiguous targets and live rename collisions (plan labels are display only; unfinished resume steps use the same guards). Folder deletes recheck names after listing items, and renames recheck after parent creation. The bw calls have no conditional write here, so a concurrent server-side change between this final check and the write remains a race; do not edit the vault elsewhere during apply. Soft trash of `trash-duplicate-of:K` (never `--permanent`; only when K exists and is not trashed, the item's `revisionDate` still equals the plan's, the type, host set and username HMAC (fresh key) still match - a `no-user` member must still have no username, a `manual` pair only needs the same type and no unique secret - and the secret relation is still `identical` / `subset`; otherwise `skipped (changed after the audit)` / `skipped (no longer a duplicate)`); empty folders deleted only when `list items --folderid` is empty; `bw sync`, `rbw sync` (`refresh_rbw`), browse index and audit file dropped. Resume: `--resume` skips steps already `ok` for the same plan sha (another sha is refused unless `--new-journal`, which archives the old journal); an interrupted step is safe again (a PUT that landed shows `ok (already)`, a trashed item has `deletedDate`, creates and renames compare by name); a plain re-run is idempotent (0 writes when nothing is left). Summary: counts per action and the scope impact per user (`td: 6 -> 11 items in scope`, counts only); skipped or failed steps are listed (exit 5). **vault-share broker** (`scripts/vault-share.py serve`, command `.local/bin/vault-share`, hub row `vault-share`, leader `v w`): td and yc never hold the master password or a vault key and run no rbw/bw of their own; they ask a small broker that runs in the OWNER's user manager next to his unlocked rbw-agent (user units `.config/systemd/user/vault-share.{socket,service}`; the socket `/run/vault-share/sock`, 0666, in an owner-owned 0755 directory that `apply-system.sh` creates; socket activation, the broker exits after 10 idle minutes and the socket stays). The inherited systemd listener uses `asyncio` `cleanup_socket=False` so idle shutdown preserves its path for the next activation; standalone test listeners retain automatic cleanup. Per connection: `SO_PEERCRED` uid -> user name -> rules from `/etc/vault-share/scopes.tsv` (re-read when mtime/size/inode change; trusted only when root-owned, not group/other-writable, no symlink, in a root-owned non-writable directory; anything else = every request `unavailable`, fail closed); the owner, root and a user without rules get `refused` before any rbw call (no lock-state oracle); 4 connections per uid, 16 in all; one request line of at most 4096 bytes within 5 s. rbw is always `/usr/bin/rbw` with a minimal environment (no `WAYLAND_DISPLAY`, `DISPLAY`, D-Bus or `GPG_TTY`), `RBW_AGENT=/usr/bin/false` (startup veto) and forwarded `PINENTRY_USER_DATA=vault-share:no-prompt`; `pinentry-themed` exits immediately on that marker before probing/executing any pinentry binary. `bw-setup` always configures this absolute wrapper path, including on a tty (the wrapper chooses curses itself); the broker validates the configured wrapper before each read request/sync and refuses unsupported arrangements. `vault-share check-rbw` and doctor `vault-share-rbw` validate the same arrangement using local config metadata only. Children have no stdin or controlling terminal; a 10 s timeout kills, drains and reaps the child. Failed list/get rechecks `rbw unlocked` without startup: a lock/agent-exit race gives `locked`, while other misses retain uniform `not_found`. The cgroup agent sweep remains defence in depth. **No cache of its own**: `list` = one `rbw list --raw`, `get`/`describe`/`totp` = one `rbw get --raw ID` whose own `folder` and `name` are checked against the scope (check and read are one response: no TOCTOU), a lookup by folder+name filters the list inside the scope first (0 hits `not_found`, several `ambiguous`); rbw's local copy is synced by the broker when its own last sync is older than 10 minutes (our writers sync after every write, so their changes apply at once; web-vault edits within 10 minutes); an item moved out of scope is unreadable at the next request. Protocol v1 (one JSON line each way): `whoami`, `list [folder]`, `describe`, `get` (1..64 field names; `username password notes uris`, card / identity / ssh keys, `field:<name>` for custom fields), `totp`; never served: the TOTP seed and the password history. The custom field `vault-share` (set by the owner) marks an item: value `totp` lets `totp` compute a code in the broker (RFC 6238 from the seed of the same response, SHA1/256/512, 6-8 digits; `steam://` refused), value `ssh` lets `private_key` out; without it `policy`. `not_found` is byte-identical for an item outside the scope and one that does not exist. Rate limits per uid in `$XDG_RUNTIME_DIR/vault-share/rate.json` (600/700, survives a restart): meta ops 60/min and 1200/h, reads 120/min and 1200/h (each field counts), codes 10/min, and 20 misses (`not_found`/`policy`/`ambiguous`) an hour pause the uid for 15 minutes on every op with one low-urgency owner notification; a locked vault notifies the owner once per user per 10 minutes. One journald line per request (`op user uid pid comm id fields result ms`), never a value or an item name (the journal is readable by wheel, td included). **Unit pitfall**: in a USER unit `ProtectSystem`, `ProtectHome`, `PrivateTmp`, `PrivateDevices`, `PrivateNetwork`, `PrivateUsers`, `Protect*` and the mount options imply `PrivateUsers=yes`, where `SO_PEERCRED` maps td and yc both to 65534 (verified with `systemd-run --user`); the unit therefore has only seccomp-type hardening (`NoNewPrivileges`, `LockPersonality`, `RestrictRealtime`, `SystemCallArchitectures`, `RestrictAddressFamilies=AF_UNIX`, `LimitCORE=0`, `UMask=0077`), the broker is non-dumpable and refuses to serve unless `/proc/self/uid_map` is the identity map; test 4.20 greps the unit. **Client** (`vault-share status | list [--folder F] [--json] | copy ITEM [--field F] | code ITEM [--print] | get ITEM --field F`; ITEM = id or `FOLDER/NAME`): connects only when `/run/vault-share` is a real directory without group/other write bits owned by another user and the server's `SO_PEERCRED` uid is that user; `copy`/`code` use `wl-copy --sensitive` + clear after 30 s (yc has no clipboard: exit 4, use `envs run`); `get` and `code --print` write to a pipe or file only, never to a terminal or under an agent (leak prevention, not a boundary). Exit codes 0 / 1 / 2 usage / 3 locked / 4 refused, policy, agent, no clipboard / 5 rate limited / 6 broker unavailable. Owner side: `vault-share status` (scope file, directory, socket unit), `report [--names]` (items in scope per user from his rbw, counts by default), `selftest` (doctor: connect as the owner and expect `refused` with the real uid), `check-scopes`, `render-scopes`. Test mode (hooks ignored otherwise): `VAULT_SHARE_TEST_DIR` below `<repo>/infrastructure/tests/`, `VAULT_SHARE_SOCK`/`_SCOPES`/`_RUNTIME` below one `VAULT_SHARE_SCRATCH` that is no real location, `RBW_BIN` below the tests; `VAULT_SHARE_TEST_PEER_FILE` (a user name read at every connection, replaces the `SO_PEERCRED` identity; td cannot reach the broker's environment), `VAULT_SHARE_TEST_AS` (the client counts as that managed user), `_TEST_UIDMAP`, `_IDLE`, `_MAX_STALE`. Test: `infrastructure/tests/vault-share/run.sh [--quick]` (fake rbw; quick 5 s, full 14 s; socket activation through `systemd-socket-activate`). **Root layer** (`sudo ./apply-system.sh --only users`, step 4c `users_vault_share`, dry-run aware): `/etc/tmpfiles.d/vault-share.conf` from `infrastructure/vault-share/tmpfiles.conf.in` (`d /run/vault-share 0755 OWNER GROUP -`, then `systemd-tmpfiles --create`), `/etc/vault-share/` (root:root 755) and `/etc/vault-share/scopes.tsv` (root:OWNERGROUP 0640, so the broker running as the owner reads it through the group, td and yc cannot), rendered AS THE OWNER by `vault-share.py render-scopes` (root never runs repo code or reads the overlay; a render failure leaves an empty temp file, the syntax check refuses it and the old file stays), then the owner's `vault-share.socket` is (re)started when his manager runs and the unit is enabled (`install.sh` enables it at the first run; `VAULT_SHARE_LOCAL_SCOPES` replaces the overlay path in the users test). `infrastructure/users/rollback.sh` removes the three paths and stops the socket. The users suite checks the rendered rows (generic + overlay, none for aimcp / tgconfirm, no `Linux/...`), the refused overlays (group-writable, symlink, invalid) and the rollback. **envs for managed users** (`managed_user()`: a non-service row of this checkout's `managed.tsv`; `ENVS_TEST_MANAGED_USER` in verified test mode): `rbw_unlocked`, `ensure_rbw`, `rbw_list`, `rbw_fields`, `env_fields` and `vault_projects` use the broker, and `rbw_run` fails for a managed user, so envs can never fall back to an rbw of its own. `env_folders(project)` = `Users/<me>/Env/<project>` then `Shared/Env/<project>` (global scope: `.../Env/global`, item `default`); `env_fields` merges the items (the user's own value wins; `SHADOWED` names are reported by `status --json` and `check`, names only); `run` asks the broker for exactly the declared names of the items (one `get` each), `status`/`check`/preview use `describe` (names and set/unset flags, no value moves). A locked vault is exit 3 with the broker's message and no prompt. Every write command (`set unset rename copy env project import convert`) exits 4 with "values in Users/td/Env are written by the owner: `envs set NAME --for td` on his terminal"; the TUI is read-only through the same refusal. **Owner side**: `--for USER` (an interactive managed user of the registry) or `--shared` on `set`, `unset`, `import`, `env`, `copy`, `diff`, `status`, `check` switches the folder root (`FOLDER_PREFIX`) to `Users/USER/Env/<project>` / `Shared/Env/<project>`; they are writes into someone else's folder, so no binding is needed, the parents (`Users`, `Users/USER`, `Users/USER/Env`) are created like `Env`, and a managed user cannot use them. The agent refusal of `envs run` stays. Test: `infrastructure/tests/envs/run.sh` section 21 (the real broker as a child process in test mode, a poison `rbw` for td that fails the run when called). **Managed-user tools**: `vault-browse` (the wrapper reads `managed.tsv` of its own checkout; a non-service row means `vault-browse.py --share --here`, otherwise `vault.sh browse`) is read-only over the broker for td and yc: the list is `list`, the preview the broker's `describe` (names, set flags, user and hosts from the list; masked, cached per run in `browse-state.PID.share.json`, no live TOTP code and no ticker because codes are rate limited), keys `y` password (card number, SSH private key, note text by type), `u` user, `o` TOTP code (marked items only), `f` field picker, Enter = `y` for logins and the picker for other types; no typing (td must not type into the owner's windows), no Trash, no `@app` row, none of `e n d r h F w S s L b O`; copies use `wl-copy --sensitive` (yc has no clipboard: the header line says `envs run`); td has no notification daemon, so a result appears in the next header line; a locked vault exits 3 and a missing runtime directory exits 1. On the owner's side the preview adds `shared  with td, yc` from `/etc/vault-share/scopes.tsv`. `linux-pass` and `bw-setup` exit 4 for a managed user before anything is called (`linux-pass`: the Linux folder is the owner's and Linux/<user> is in no scope, he runs `linux-pass --update td` after the passwd; `bw-setup`: no rbw configuration, no bw login; test hooks `LINUX_PASS_AS_USER` / `BW_SETUP_AS_USER` can only make a run count as managed); the check is `managed_users interactive` captured in a variable, never piped into `grep -q` (pipefail + early exit = 141). `profiles/cli.txt` links `vault-share` and `vault-browse`. Tests: `infrastructure/tests/vault-browse/run.sh` section 16 (quick) with the real broker as a child process. **Honest threat model of vault-share**: (1) the owner's uid: every process of skalse, agents included, reads the whole vault while rbw is unlocked (`rbw get`), as before; it can also edit the broker code and `scopes.local.tsv`, but widening td's effective scope still needs the owner's sudo (`/etc/vault-share/scopes.tsv` is root's). (2) What a td process, its agents included, can do with the socket: list folder and item names, usernames and hosts of td's scope; read every servable field of every item in the scope (passwords, notes, hidden fields); get codes for items marked `vault-share: totp` and private keys only for items marked `ssh`; learn whether the owner's vault is unlocked (a presence oracle given only to listed users); use up its own rate limit (a DoS of td's envs) and add bounded lines to the owner's journal. (3) What it cannot do: write, lock, unlock, trigger a pinentry window, read anything outside the scope or learn that it exists (uniform `not_found`), read TOTP seeds or password history, act as yc (`SO_PEERCRED`; user namespaces do not change the uid seen in the init namespace). (4) **td reads exactly td's scope only while it stays td**: td and yc are in the `docker` and `wheel` groups (`/run/docker.sock` is 0660 group docker), so any td process can become root without a password (`docker run -v /:/host ...`) and then read the owner's vault while it is unlocked; the broker ends "td's agents hold the whole vault" for naive and prompt-injected access, it is not a boundary against a td agent that deliberately escalates. **Follow-up, decided but not part of this stage: ROOTLESS** - td and yc leave the `docker` group and get rootless docker per user (wheel stays); until then this limit stands, and `Linux/<user>` is in no scope so that the Linux passwords are not handed to the same agents on top of it. (5) Aimcp, tgconfirm, greeter, containers (uid 0) and root are refused before any vault access, with no lock-state oracle. (6) Values pass through the broker's memory and its rbw children (non-dumpable, `LimitCORE=0`; Python strings cannot be wiped); the journal lines carry no value and no name; a value that was served cannot be taken back, so shrinking a scope means rotating what it covered. (7) The client-side guards (`get` to a pipe only, `envs run`'s agent refusal) are leak prevention, not isolation.
